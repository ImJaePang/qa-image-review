# 사용 가이드: 지금까지 구현된 것과 사용 방법

> 마지막 갱신: 2026-11-04. 설계 이유는 [design.md](design.md), 진행 현황·다음 할 일은 [../README.md](../README.md), 개념 설명은 [study-notes.md](study-notes.md).

## 1. 이 프로젝트가 하는 일

AI가 만든 이미지를 **모델이 먼저 검사(사전 검증)** 하고, **QA 담당자가 화면에서 승인/반려**하는 검수 시스템의 연습용 미니 프로젝트다.

```
이미지 파일 ─→ [수신 워커] ─→ 모델 추론(점수·이상 영역 박스) ─→ 판정(정상/의심/불량)
                                                                      │
관리자: 의심·불량을 골라 담당자에게 배정 ◀──────────────────────────────┘
QA 담당자: 점검 시작 → 이미지 한 장씩 승인/반려 → 점검 완료
관리자: 확인 완료 · 소요 시간 분석 보기
```

**규칙**: 회사 데이터·자료는 절대 쓰지 않는다. 연습 데이터는 직접 만든 것만 쓴다(목 데이터, ComfyUI로 만든 이미지).

## 2. 구성

| 폴더 | 내용 |
|---|---|
| `frontend/` | 화면. React + Vite + TypeScript + Tailwind + shadcn/ui |
| `backend/` | API 서버(Fastify), 수신 워커, 이미지 생성·적재 스크립트 |
| `db/` | `init/` 최초 스키마·시드, `migrations/` 이후 변경 SQL |
| `docker-compose.yml` | PostgreSQL 16 컨테이너 |
| `data/images/` | 이미지·히트맵·사본 (git 제외). 생성 이미지는 `real/`, 수신 폴더는 `ingest/` |
| `docs/` | 기획서(plan), 설계(design), 학습 노트, 이 문서 |

프로세스는 최대 네 개가 따로 돈다: **DB**(Docker), **API 서버**, **프론트 개발 서버**, (선택) **수신 워커**.

## 3. 구현된 기능

### 화면 (프론트엔드)
- 로그인/회원가입, 라이트/다크 테마. **가입은 승인 신청**이다: 신청 권한(QA/연구원)을 고르면 `승인 대기`로 만들어지고 바로 로그인되지 않는다. 승인 화면은 아직 없어 DB에서 `UPDATE users SET status='ACTIVE', role=... WHERE email=...`로 한다(사용자 관리 화면은 다음 단계). 로그인 시 상태별 안내(승인 대기/만료/비활성)는 비밀번호가 맞을 때만 나오고, 로그인할 때마다 사용기한이 1년 뒤로 갱신된다. 이미 받은 로그인 토큰도 비활성·만료되면 바로 막힌다.
- **배정 목록**: 상태별 건수 카드, 상태 필터·검색, 페이지 이동
- **신규 배정**(관리자): 담당자·마감일·판정(정상/의심/불량)·장수를 정하면 미배정 이미지가 **점수 낮은 순**으로 담긴다
- **배정 상세**: 단계 표시(배정 → 점검중 → 점검완료 → 확인완료), 개요, 점검 내용 메모, 상태 변경 이력
- **이미지 검수**: 3천 장도 부드럽게(서버 페이지네이션 + 가상 스크롤 + 낙관적 업데이트)
  - 이미지 위에 **이상 영역 박스**와 **히트맵** 겹쳐 보기(둘 다/히트맵/박스/끄기, 투명도 조절)
  - **보기 모드**: `미리보기`(줄인 사본, 기본) / `원본 고정`(원본, 다음 2장은 미리 받음). 선택은 브라우저에 저장
  - 오른쪽 패널: AI 점수·판정, 이상 영역별 사유, 코멘트, 승인/반려, **마지막 검수자·시각**
- **소요 시간 분석**(관리자): 담당자별 검수 속도, 배정별 소요, 모델 처리 시간, 수신 배치 기록

### 서버
- 인증(JWT httpOnly 쿠키), 역할별 권한(관리자/QA)
- 배정 생성·상태 전이(정해진 다음 단계로만)·점검 내용·이미지 페이지 조회·검수 저장
- **이미지 파일 API** `GET /api/images/:imageKey/thumb|preview|original|heatmap`: 디스크 경로를 노출하지 않고 이미지 ID로 요청. 관리자는 전부, QA는 **자기 배정 이미지만**. 캐시·보안 헤더 적용
- 판정은 `rules` 테이블의 임계값으로만 하고, 판정마다 **모델 버전과 규칙 버전**을 기록

### 파일 수신 워커 (`npm run worker`)
`inbox` 폴더에 이미지를 넣으면 자동으로: 안정 판정(복사가 끝난 파일만) → 매직바이트 검사 → 해시 기록 → 한 장씩 추론 → 판정 저장 → 썸네일·미리보기(webp) 생성 → `done`으로 이동. 실패하면 `failed`로 격리하고 큐는 계속 돈다. 워커는 하나만 실행되고(DB 잠금), 시작할 때 죽다 만 작업을 정리한다.

### 모델 연결부
추론은 **어댑터**로 분리돼 있고 출력은 기획서 5장 JSON 계약으로 고정이다. 지금은 **목 어댑터**(파일 해시로 만든 가짜 점수·박스)만 있다. 실제 모델은 같은 모양의 어댑터를 추가하면 된다.

### 데이터 만들기
- `generate-mock.mjs`: SVG 목 이미지 3천 장(부하 테스트용)
- `generate-real.mjs`: **ComfyUI로 실제 PNG** 생성(정상 + 생성 오류 6종, 정답 박스 기록)
- `make-derivatives.mjs`: 이미 수신된 이미지의 썸네일·미리보기 보충

## 4. 처음 실행하기

필요한 것: Node.js 22, Docker Desktop. (이미지 생성은 추가로 ComfyUI.)

```bash
# 1) 환경 파일 (.env는 git에 올리지 않는다)
cp .env.example .env          # 비밀번호·JWT_SECRET(16자 이상) 수정

# 2) DB
docker compose up -d          # 최초 기동 시 db/init/*.sql 자동 적용

# 3) 백엔드
cd backend
npm install
npm run migrate               # 스키마 변경분 적용 (이미 적용된 것은 건너뜀)
npm run load-mock             # 최초 1회: 목 데이터 3천 장 생성 후 DB 적재
npm run dev                   # API 서버, 포트 3000

# 4) 프론트 (다른 터미널)
cd frontend
npm install
npm run dev                   # 화면 http://localhost:5173
```

> **포트 3000이 `EACCES`로 안 열리면** (윈도우가 예약한 범위): backend와 frontend 둘 다 `API_PORT=3101`을 앞에 붙여 실행한다. 예: `API_PORT=3101 npm run dev`.

**데모 계정** (비밀번호는 모두 `1234`): `admin@example.com`(관리자), `qa1@example.com`(김검수), `qa2@example.com`(이점검), `qa3@example.com`(박확인)

**끌 때**: 각 터미널에서 Ctrl+C, DB는 `docker compose down`. (`-v`를 붙이면 **데이터가 지워진다**.)

## 5. 화면 사용 흐름

### 관리자
1. **신규 배정**: 배정 목록에서 `신규 배정` → 담당자·마감일·판정·장수 → 생성. 이미 배정된 이미지는 다시 담기지 않는다.
2. 담당자가 점검을 끝내면 **확인 완료**. (사전배치 단계는 없다: 이미지는 수신할 때 이미 추론·판정된다)
3. 메뉴 **소요 시간**에서 검수 속도·모델 처리 시간 확인.

### QA 담당자
1. 배정 상세에서 **점검 시작** → `이미지 검수` 탭. 처음 열면 첫 미검토 이미지로 이동한다.
2. 이미지를 보고 **승인/반려**(코멘트는 선택). 저장되면 다음 미검토로 넘어간다.
3. 전부 검수하면 **점검 완료** (미검토가 남아 있으면 거부된다).

### 단축키 (검수 화면)
| 키 | 동작 |
|---|---|
| `←` `→` | 이전/다음 이미지 |
| `A` | 승인 |
| `R` | 반려 |
| `H` | 오버레이(박스·히트맵) 켜기/끄기 |
| `O` | 원본 고정 ↔ 미리보기 |

코멘트 입력칸에 커서가 있을 때는 단축키가 동작하지 않는다.

## 6. 파일 수신 사용법

```bash
cd backend && npm run worker     # API와 별도 프로세스. 하나만 실행 가능
```

1. 이미지를 `data/images/ingest/inbox/` 에 넣는다. (확장자 png/jpg/jpeg/webp/svg, 파일당 50MB 이하, 5초마다 스캔. 복사 중인 파일은 크기·수정시각이 두 번 연속 같을 때만 받는다)
2. 흐름: `inbox` → `processing`(대기·처리 중) → `done`(성공) 또는 `failed`(실패, 사유는 DB `images.error`).
3. 처리가 끝난 이미지는 미배정 상태로 쌓이고, 관리자가 신규 배정으로 담는다.
4. 같은 파일을 다시 넣어도 막지 않는다. 새 이미지로 쌓이고 `origin_image_id`로 처음 수신본과 연결된다.
5. 워커가 죽었다 다시 켜지면 처리 중이던 건을 대기로 되돌려 이어서 처리한다.

### 연계 관리 화면 (관리자, 설정 > 연계 > 연계 관리)
- **목록**: 연계마다 사용 중/꺼짐, 감시 폴더·확장자·주기, 대기/처리 중/완료/실패 건수, 최근 수신 시각. 10초마다 갱신된다.
- **추가**: 이름과 폴더를 정한다. 폴더는 허용 루트(`INGEST_ROOT`, 기본 `data/images/ingest`) 아래 상대 경로이고, 다른 연계가 쓰는 폴더와 겹치면 거부한다(같은 폴더를 두 스캐너가 보면 같은 파일을 두 번 받는다). 새 연계의 폴더는 `source-N/` 아래로 제안한다.
- **수정**: 이름·폴더·확장자·크기 상한·스캔 주기. 워커가 매 주기 DB에서 읽으므로 **워커를 다시 켜지 않아도 반영**된다. 변경 이력(누가·언제·이전 값 → 바뀐 값)이 아래에 쌓인다.
- **끄기/켜기**: 삭제는 없다(이미 받은 이미지가 연계를 가리키므로). 끄면 새 파일을 받지 않을 뿐, 이미 받은 파일의 판정은 계속된다.
- **실패 건 재시도**: 실패 건수가 있으면 "실패 N건 보기 · 재시도"가 나온다. 파일이 실패 폴더에 있는 건만 처리 중 폴더로 되돌리고 새 수신 배치로 묶는다. 이미지가 아니어서, 또는 크기 상한을 넘어서 실패한 건은 설정을 고치지 않으면 다시 실패한다.

## 7. 실제 이미지 만들기 (ComfyUI)

1. ComfyUI 실행: `H:\jjal\run_comfyui.bat` (또는 `ComfyUI_windows_portable\run_nvidia_gpu.bat`). 브라우저에서 `http://127.0.0.1:8188` 이 열리면 준비된 것.
2. 생성:
   ```bash
   cd backend
   node scripts/generate-real.mjs --count 300
   ```
   - 모델: Z-Image-Turbo + 증류 LoRA(4스텝). 정상 이미지 약 11~16초/장, 300장 약 70분.
   - 오류 이미지(기본 30%)는 정상 이미지의 일부 영역을 망가뜨린 것: `TEXTURE_ANOMALY`, `SHAPE_DISTORTION`, `PART_COUNT_MISMATCH`(인페인팅), `COMPOSITE_EDGE`, `LIGHTING_MISMATCH`, `SCALE_ANOMALY`(합성).
   - 중간에 끊겨도 같은 명령을 다시 실행하면 이어서 만든다.
3. 결과: `data/images/real/`
   - `original/` 검수 대상 PNG(1344×768), `base/` 오류 이미지의 정상본
   - `ground_truth.jsonl`: 시드·프롬프트·**정답 박스**·오류 종류 (나중에 실제 모델 평가에 쓴다)
4. 수신 확인: `real/original/*.png` 를 `ingest/inbox/` 로 복사하고 워커를 켠다. (300장 약 30초)

옵션: `--count`, `--defect-ratio 0.3`, `--seed 1000`, `--steps 4`, `--lora <파일명>`, `--out <폴더>`, `--width/--height`.
프롬프트에는 일반 표현만 쓰고 회사 자료·특정 기종명은 넣지 않는다.

## 7-2. 규칙 관리 (관리자, 설정 > 판정 > 임계값/규칙)
화면 구성: 현재 활성 버전과 "재판정 필요" 건수 / 새 버전 만들기(입력하면 **미리보기**로 정상·의심·불량이 몇 장이 되고 몇 장이 바뀌는지) / 재판정(미배정만 또는 배정된 이미지 포함) / 버전 목록(끄기·켜기 = 되돌리기) / 변경 이력. 아래는 화면이 쓰는 API.

판정 임계값(정상 ≥ `normalMin`, 의심 ≥ `suspectMin`, 그 아래 불량)은 `rules` 테이블에 있고 **수정하지 않고 새 버전을 쌓는다**. 활성 규칙 = 켜진 것 중 가장 높은 버전(워커도 같은 기준).

| 요청 | 하는 일 |
|---|---|
| `GET /api/rules` | 버전 목록, 활성 버전, **다시 판정이 필요한 이미지 수**(미배정/배정, 활성 규칙이 아닌 규칙으로 판정된 것) |
| `GET /api/rules/preview?normalMin=0.8&suspectMin=0.4` | 저장하지 않고 "이 값이면 정상/의심/불량이 몇 장이 되고, 몇 장이 바뀌는지" |
| `POST /api/rules` `{normalMin, suspectMin}` | 새 버전 생성(바로 활성). 새로 수신하는 이미지부터 이 규칙으로 판정. **이미 판정된 이미지는 그대로** |
| `POST /api/rules/:id/rejudge` `{scope}` | 저장된 점수에 활성 규칙을 적용해 판정을 추가. `scope`: `unassigned`(기본, 미배정만) / `all`(배정된 이미지까지) |
| `PATCH /api/rules/:id` `{enabled}` | 끄기/켜기. **새 버전을 끄면 이전 버전이 활성이 된다(되돌리기)** — 이후 재판정을 눌러야 판정도 돌아간다. 켜진 규칙이 하나뿐이면 못 끈다 |
| `GET /api/rules/history` | 누가·언제 만들고 켜고 끄고 재판정했는지 |

- 재판정은 모델을 다시 돌리지 않는다. 옛 판정 행은 지우지 않고 그대로 남는다(어떤 규칙 버전으로 판정했는지 기록).
- 기본이 "미배정만"인 이유: 검수자가 보고 있는 AI 판정이 갑자기 바뀌지 않게 하려는 것. 배정된 이미지까지 바꾸려면 `scope: "all"`을 명시한다.

## 9. 문제 해결

| 증상 | 원인·해결 |
|---|---|
| API가 `listen EACCES 127.0.0.1:3000` | 윈도우 예약 포트. `API_PORT=3101`로 backend·frontend 모두 실행 |

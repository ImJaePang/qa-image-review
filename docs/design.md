## 2. 프론트엔드 (`frontend/`)

### 스택
Vite 8 + React 19 + TypeScript(7) + Tailwind v4 + shadcn/ui(Base UI 기반) + React Router + Zustand + TanStack Query.
경로 별칭 `@` → `src`. 강조색은 진한 연두(`index.css`의 `--primary`, 라이트 `oklch(0.58 0.19 135)` / 다크 `oklch(0.76 0.2 135)`).

### 화면 구성
- 로그인 전: `/login`, `/signup`. 미로그인 접근 시 로그인으로 이동.
- 로그인 후 레이아웃: 상단(로고, 상위메뉴, 사용자/역할, 다크모드 전환, 로그아웃) / 좌측(선택한 상위메뉴의 중메뉴·소메뉴) / 우측(소메뉴 화면).
- 메뉴는 DB(`menus`)가 정하고 서버가 내 권한으로 볼 수 있는 것만 내려준다(`/api/menus/mine`). 화면 경로 연결은 `App.tsx`. (초기에는 구현된 화면이 `/review/assignments`뿐이고 나머지는 `Placeholder`였으나 2026-11-14에 모든 메뉴 화면이 구현되어 `PLACEHOLDER_PATHS`는 비어 있다.)
- 배정 리스트: 상태 요약 카드, 검색, 상태 필터, 페이지네이션. 행 클릭 → 상세 모달(`?id=` 쿼리로 열림).
- 신규 배정 모달(관리자만): 배정명, 담당자, 마감일, 대상 AI 판정, 이미지 수 → 미배정 이미지 자동 선택.
- 상세 모달 탭: 개요 / 이미지 검수 / 점검 내용·이력.
  - 이미지 검수: 점수 낮은 순 목록, 박스·히트맵 오버레이(둘 다/히트맵/박스/끄기, 투명도), 사유 코드 뱃지, 승인/반려, 단축키 `←` `→` `A` `R` `H`.
  - 모달 vs 탭은 모달 안 탭으로 결정. 수천 장 연속 검수 시에는 전용 페이지(`/review/assignments/:id`)로 옮기는 안을 보류 중 (컴포넌트 그대로 이동 가능).

### 상태 흐름과 권한
배정 → 점검중 → 점검완료 → 확인완료 (사전배치 단계는 마이그레이션 002에서 제거, 8장 참고)

| 현재 상태 | 다음 단계 버튼 | 가능한 사람 |
|---|---|---|
| 배정 | 점검 시작 | 담당자, 관리자 |
| 점검중 | 점검 완료 (미검토 이미지가 남으면 거부) | 담당자, 관리자 |
| 점검완료 | 확인 완료 | 관리자 |

이미지 검수(승인/반려)는 `점검중` 상태에서 담당자(또는 관리자)만 가능.

### API 연동 구조
- `src/api/client.ts`: fetch 래퍼(같은 출처 `/api`, 쿠키 세션, 에러는 `{message}` → `ApiError`). 401을 받으면 인증 스토어가 로그아웃 상태로 전환.
- `src/api/mappers.ts`: 서버 영문 코드 ↔ 화면 한글 값 변환 한 곳. 화면 코드는 한글 값만 다룬다.
- `src/api/index.ts`: `api` 객체(함수 시그니처는 Promise 기반). 개발 중 Vite가 `/api`를 백엔드(3000)로 프록시.
- `src/stores/auth.ts`: 서버 세션(httpOnly 쿠키) 기반. 앱 시작 시 `/auth/me`로 확인(`ready`). 비밀번호나 계정을 브라우저에 저장하지 않는다.
- 회원가입 화면의 역할 선택은 제거했다 (서버가 항상 `qa`로 만든다).
- `src/lib/domain.ts`: 사유 코드 한글 라벨. 판정은 서버가 `rules` 기준으로 내려준다.
- 이미지 검수 패널: 전체 장수만큼 가상 행을 잡고(`@tanstack/react-virtual`), 보이는 행·현재 이미지가 속한 50장 단위 페이지만 `useQueries`로 불러온다(3천 장에서 DOM 행 약 20~30개). 열 때 첫 미검토로 이동하고, 승인/반려 뒤에는 바로 다음이 미검토면 그대로 이동, 아니면 서버에 다음 미검토 위치를 묻는다. 승인/반려는 낙관적 업데이트 후 실패하면 되돌림.

### 알려진 한계
- 이미지 검수 도구 모음이 좁은 화면에서 두 줄로 내려간다.
- 검수 완료 여부는 서버가 최종 판단하지만, 점검 완료 버튼의 사전 안내는 화면의 건수 기준이다.
- 목록은 썸네일 생성 전이라 원본 SVG를 그대로 쓴다.
- 서버 에러 메시지가 한글 문장이다 (다국어 시 에러 코드 방식으로 변경 필요, 6장).

## 3. DB (`db/init/`)

실행: `docker compose up -d` (최초 기동 때 `01_schema.sql`, `02_seed.sql` 자동 실행). 스키마 변경 반영은 `docker compose down -v` 후 재기동(데이터 삭제됨).

### 테이블

| 테이블 | 용도 |
|---|---|
| `users` | 계정. 역할 `admin` / `qa`. 비밀번호는 bcrypt 해시(pgcrypto) |
| `images` | 이미지 한 장. 원본/미리보기/썸네일 경로. 외부 노출용 `image_key`(예: img_0001) |
| `model_runs` | 모델 1회 실행. 모델 버전, 전체 점수, 히트맵 경로, 처리 시간(`duration_ms`) |
| `detections` | 실행당 이상 영역 박스. 좌표는 원본 픽셀 기준, 점수, 사유 코드 |
| `rules` | 판정 규칙. `params` jsonb(`{"normalMin":0.9,"suspectMin":0.5}`), 버전 |
| `verdicts` | 실행 결과 + 규칙 → 판정(NORMAL/SUSPECT/DEFECT). 어떤 규칙 버전인지 `rule_id` 기록 |
| `assignments` | 배정 1건. 상태, 담당자, 마감일, 점검 내용. `code`(AS-0001)는 id에서 자동 생성 |
| `assignment_images` | 배정↔이미지 소속 + 배정 시점의 AI 결과(`run_id`) + 정렬 순서 |
| `assignment_history` | 상태 변경/처리 이력(from/to, 행위자, 시각). 단계별 소요 시간의 원천 |
| `reviews` | 검수 결과. **쌓기만 하는 기록**(번복 시 행 추가), 최신 행이 현재 상태 |
| `batch_jobs` | (폐기) 사전배치 실행 기록. 002 이후 기록하지 않고 과거 기록만 보존. 수신 배치는 `ingest_batches` |

뷰: `review_current`(이미지별 최신 검수 상태), `assignment_summary`(배정 리스트용 장수·판정 분포·검수 진행).

### 값 코드 (영문 저장, 한글은 화면에서 매핑)
- 배정 상태: `ASSIGNED`(배정) `IN_REVIEW`(점검중) `REVIEWED`(점검완료) `CONFIRMED`(확인완료)
- 판정: `NORMAL`(정상) `SUSPECT`(의심) `DEFECT`(불량)
- 검수: `APPROVED`(승인) `REJECTED`(반려) — 행이 없으면 미검토
- 사유 코드: 기획서 4장 6종 그대로 (`COMPOSITE_EDGE` 등)

### 설계 결정과 이유
- **`reviews`를 별도 테이블로**: 한 배정에 3천 장 규모이고, 재점검으로 같은 이미지가 다시 배정될 수 있으며, 번복 횟수 같은 분석이 필요해서. 미검토는 행이 없는 것으로 표현해 3천 행을 미리 만들지 않는다.
- **`assignment_images.run_id`**: 모델을 다시 돌려도 "검수자가 그때 본 결과"가 보존되도록.
- **소요 시간은 서버가 저장한 시각으로 계산** (클라이언트 측정값 불신, 자리를 비운 시간이 섞이는 문제 때문):
  - 배정 단위 평균 = (점검중→점검완료 시각, `assignment_history`) ÷ 검수한 이미지 수.
  - 이미지별 작업 속도 = 같은 담당자의 연속된 `reviews.decided_at` 간격. 약 5분 이상 벌어진 구간은 자리를 비운 것으로 보고 제외(기준은 쿼리에서 조정).
  - 수신 배치 시간 = `ingest_batches`, 모델 1장 시간 = `model_runs.duration_ms`.
- **인덱스**: `assignment_images(assignment_id, position)`, `reviews(assignment_id, image_id, decided_at DESC)`, `detections(run_id)` 등 3천 장 집계를 염두에 둠.

## 3-1. 백엔드 API (`backend/src`)

Fastify 5, ORM 없이 `pg` 직접 사용. 입력은 라우트별 JSON Schema로 검증. 에러 응답은 `{ message }`.
인증: 로그인 시 JWT를 httpOnly 쿠키(`token`, 12시간)로 발급, `Authorization: Bearer`도 허용. 이미지는 `<img>`가 쿠키를 자동 전송하도록 이 방식을 택했다. 프론트는 Vite 프록시로 같은 출처에서 호출할 것(CORS 불필요).

| 메서드 경로 | 설명 | 권한 |
|---|---|---|
| POST /api/auth/login, signup, logout / GET /api/auth/me | 가입은 항상 qa 역할 | - |
| GET /api/users | 담당자 선택용 | 로그인 |
| GET /api/assignments?status&q&page&pageSize | 목록 + 상태별 건수 | 로그인 |
| GET /api/assignments/:code | 상세(건수, 이력, 점검 내용). 이미지는 제외 | 로그인 |
| GET /api/unassigned-counts | 미배정 이미지 수(판정별) | 로그인 |
| POST /api/assignments | 신규 배정. 미배정 이미지 자동 선택, 순서는 점수 낮은 순 | 관리자 |
| POST /api/assignments/:code/status {to} | 정해진 다음 단계로만. 점검 완료는 미검토가 남으면 거부 | 단계별(아래) |
| PUT /api/assignments/:code/note | 점검 내용 저장 | 담당자·관리자 |
| GET /api/assignments/:code/images?filter&verdict&page&pageSize | 서버 페이지네이션(최대 200). filter: all/unreviewed/approved/rejected | 로그인 |
| PUT /api/assignments/:code/images/:imageKey/review | 승인/반려 저장. 점검중일 때만 | 담당자·관리자 |
| GET /api/monitoring/time?gapMinutes=5 | 소요 시간 분석(담당자별·배정별·모델·수신 배치). 자리 비움 기준 1~120분 | 관리자 |
| GET /api/images/:imageKey/thumb|preview|original|heatmap | 이미지·히트맵 파일(이미지 ID 기반, 경로 비노출). 관리자 전부, QA는 자기 배정 이미지만, `ingest_status=DONE`만. `Cache-Control: private` + ETag(304), nosniff, SVG는 CSP sandbox | 로그인 |

- 단계별 권한은 2장 표와 같다 (확인 완료는 관리자, 점검 시작·완료는 담당자 또는 관리자).
- 사전배치 단계는 없다. 이미지는 수신 시점에 추론·판정되고(`npm run worker`), 신규 배정은 `ingest_status=DONE`인 이미지만 담는다. 모델 연동 지점은 어댑터(`src/model/`).
- 검수 저장은 직전과 같은 내용이면 행을 추가하지 않는다 (소요 시간 분석 노이즈 방지). 판정을 바꾸면 행 추가.
- 신규 배정은 `pg_advisory_xact_lock`으로 직렬화해 두 배정이 같은 이미지를 집지 않게 한다.
- 이미지 항목: 5장 계약 필드 + `verdict`, `reasons`, `thumbUrl/previewUrl/heatmapUrl`, `review{status: NONE|APPROVED|REJECTED}`. 썸네일 생성 전에는 원본 URL을 그대로 돌려준다.
- 상태·판정 값은 영문 코드로 응답한다. 한글 매핑은 프론트 몫.
- 검증: `backend/test/`의 통합 테스트(`npm test`)가 권한·상태 전이·검수·페이지네이션·파일 접근을 확인한다. 테스트 전용 DB를 매번 새로 만들어 스키마·시드를 적용하므로 개발 DB와 섞이지 않는다.
- `GET /api/assignments/:code/next-unreviewed?after=N`: N번째 뒤의 첫 미검토 위치(없으면 처음부터, 전부 검토했으면 null). 이어서 검수할 때 화면이 첫 미검토로 바로 이동하는 데 쓴다.
- 로그인 시도 횟수 제한은 구현됨(아래 "로그인 시도 횟수 제한"). (`@fastify/static`은 파일 API 전환으로 제거되어 관련 npm audit 경고도 사라졌다.)

### 소요 시간 분석 계산 기준 (`routes/monitoring.mjs`)
- **담당자별 이미지당 시간**: 같은 담당자·같은 배정에서 연속된 `reviews.decided_at` 간격. 기준(기본 5분) 초과 간격은 자리 비움으로 보고 평균/실작업 시간에서 제외하고 "자리 비움 구간" 수로 따로 센다. 다른 담당자의 검수가 사이에 끼어도 서로의 간격에 영향이 없다(담당자·배정 단위로 계산).
- **번복**: 같은 이미지를 다시 판정한 행도 하나의 작업 간격으로 계산하고, 건수는 `번복 = 판정 횟수 - 이미지 수`로 따로 보여 준다.
- **배정별**: (점검 시작 ~ 점검 완료 시각, `assignment_history`) ÷ 검수한 이미지 수 = 평균/장. 실작업/장은 자리 비움을 뺀 값. 배정~확인은 ASSIGNED ~ CONFIRMED. 아직 끝나지 않은 단계는 null.
- **모델**: `model_runs.duration_ms`의 평균/p95/최대(버전별). **수신 배치**: `ingest_batches` 시작·종료 시각, 끝나지 않은 건은 null (과거 `batch_jobs`는 더 이상 쓰지 않음).
- 첫 검수는 직전 기준이 없어 간격에 포함되지 않는다. 점검 시작 직후 첫 이미지를 보는 시간은 배정별 평균(점검 시작 기준)에만 반영된다.
- 한계: 한 번에 많은 이미지를 승인하는 일괄 처리가 생기면 간격이 매우 짧게 잡힌다. 현재 화면에는 일괄 처리가 없다.

## 8. 결정: 파일 수신 시 사전 검증 (구현 예정, 2026-11-02)

**배경**: 신규 배정은 "AI 판정이 의심/불량인 것"을 골라 담으므로 배정 시점에 AI 결과가 이미 있어야 한다. 지금의 `사전배치`(배정 후 실행)는 이 순서와 맞지 않는다.

### 확정된 결정
- 연계로 들어오는 **파일만** 받는다. 상대 DB는 지금 필요 없다 (실제 환경을 모르므로 보류). 흐름은 "폴더 감시 → 내 DB에 기록 → 순차 추론 → 검수 → 내 DB 갱신".
- 파일은 **이동** 방식이다 (`inbox → processing → done / failed`). 복사는 혼란만 키운다.
- 수신 즉시 **순차 배치로 사전 검증(추론)** 한다. 새 흐름: 수신 → 추론 → 판정 → 배정 → 점검 → 확인.
- **상태 흐름에서 `사전배치`(PRECHECKED)는 빠진다.** (배정 → 점검중 → 점검완료 → 확인완료, 4단계)
- 신규 배정은 추론이 끝난 이미지만 대상으로 한다 (대기·실패 이미지 제외).
- 모델 호출부는 **어댑터**로 분리하고 출력은 5장 JSON 계약으로 고정한다. 현재의 목 생성기가 첫 번째(가짜) 구현이 된다.
- 규칙(임계값)만 바뀌면 추론 없이 재판정한다. 모델을 바꿔 다시 돌리는 것은 같은 방식으로 새로 수신해 처리한다 (아래 중복 정책).
- 감시는 **주기 스캔**(기본 5초, 설정 가능) + 복사 중인 파일은 크기·수정시각이 2회 연속 같을 때만 수신. 워커는 API와 **별도 프로세스**(`npm run worker`), 동시성 기본 1. 설정은 DB에 두고 워커가 매 주기 읽는다.
- 작업 큐는 별도 브로커 없이 DB 테이블 (`FOR UPDATE SKIP LOCKED`). 워커가 죽어 `PROCESSING`에 멈춘 건은 시작 시 `PENDING`으로 되돌린다.
- 테스트를 위해 `scanOnce()`(폴더 1회 훑기)와 `processOne()`(대기 1건 처리)를 타이머와 분리해 만든다. 임시 폴더 + 목 어댑터 + 실패 주입 어댑터로 검증.

### 같은 파일이 다시 들어올 때 (중복 정책)
- **막지 않는다.** 모델 버전이 바뀐 뒤 재검증처럼 같은 파일을 다시 검증하고 싶을 수 있다.
- 수신할 때마다 `images`에 **새 행을 insert** 한다. 새 행은 자기 경로, 추론 결과, 검수 결과를 따로 가진다. 그래서 이미 검수 중인 이미지에 영향이 없다.
- 같은 내용인지는 파일 **해시(sha256)** 로 안다 (파일 이름은 믿을 수 없다). 새 행은 `origin_image_id`(자기 참조 외래키)로 같은 해시의 **가장 처음 수신 행**을 가리킨다. 처음 수신한 것은 NULL. 해시는 막는 용도가 아니라 연결·표시용이다.
- 같은 이름의 파일이 이동 중 충돌하지 않게, 이동 후 파일명은 `image_key`(고유값)로 정한다. 원래 파일명은 `source_name`에 보존.
- 신규 배정이 같은 원본의 여러 행을 한꺼번에 담을지는 구현 때 결정 (기본: 허용, 화면에 "재수신" 표시).

### 관리자 메뉴 `연계 관리` — 설정·추가 화면 (모니터링이 아님)
사용자 의도: 연계를 **설정하고 추가하는** 화면. 진행 현황 상세는 모니터링 메뉴의 몫이고, 여기서는 연계별 현재 상태만 요약해서 보여준다.
- 구조: 연계 목록 + 추가/수정/삭제/켜기·끄기. 연계 하나 = 종류(현재 `FOLDER`, 이후 `DB` 등) + 이름 + 종류별 설정 + 사용 여부. 신설 테이블 `integrations` (설정은 `config jsonb`).
- 폴더 연계 설정 항목: 감시 폴더, 완료/실패 폴더, 파일 패턴(확장자), 스캔 주기, 한 번에 처리할 장수, 일시정지/재개.
- 목록에 연계별 요약 상태: 최근 수신 시각, 대기/처리중/완료/실패 건수, 실패 건 재시도 버튼.
- 보안: 관리자 전용, 경로는 허용 루트(`INGEST_ROOT`) 하위만 허용, 심볼릭 링크 불추적, 파일 앞부분(매직바이트)으로 이미지 확인, 크기 상한, 설정 변경 이력(누가·언제·무엇) 기록.
- 화면 구성(목록/상세 폼/이력)은 구현 단계에서 목업을 먼저 만들어 사용자와 정한다.
- 결과 내보내기(검수 결과를 outbox 폴더에 JSON/CSV로 쓰기)는 자리만 두고 나중에 `integrations` 종류 하나로 추가한다.

### 배치의 단위
- "수신 배치" = 스캔 1회에 발견된 파일 묶음. 신설 `ingest_batches`(전체/처리/실패 수, 시작·종료 시각). 기존 `batch_jobs`는 배정 단위라 이 역할로 쓸 수 없어 대체한다. 소요 시간 분석의 사전배치 항목은 이쪽을 기준으로 바꾼다.

### DB·코드 영향 (변경 시 같이 고칠 곳)
- `images`: `sha256`, `source_name`, `source_path`, `ingest_status`(PENDING/PROCESSING/DONE/FAILED), `error`, `received_at`, `origin_image_id`, `batch_id` 추가. 신설: `ingest_batches`, `integrations`, 설정 변경 이력. 마이그레이션 스크립트 방식으로 적용.
- `assignments.status` CHECK에서 `PRECHECKED` 제거 (기존 PRECHECKED 데이터는 ASSIGNED로 이전), `batch_jobs` 대체.
- 서버 `TRANSITIONS`와 신규 배정 조건(`ingest_status='DONE'`만), 프론트 상태 단계 표시·요약 카드(5칸 → 4칸), `mappers.ts`, 소요 시간 화면의 "사전배치" 카드·표, 관련 테스트(`monitoring.test.mjs`의 PRECHECKED 이력·batch_jobs 시나리오, `api.test.mjs`의 배정 흐름).

### 순서 (①은 완료, 아래 "1단계 구현 메모" 참고)
① 마이그레이션 + 모델 어댑터 인터페이스 + 목 구현 → ② `scanOnce`/`processOne` + 워커 프로세스 + 테스트 → ③ PRECHECKED 제거 (백엔드·프론트·테스트) → ④ 연계 관리 화면. 각 단계마다 테스트가 통과한 상태에서 커밋한다.

### 공통 컬럼 (미정, 의견만 정리)
사용자가 생각한 공통 컬럼: `id`, 등록자, 등록일시, 수정자, 수정일시. 상속(`INHERITS`)은 제약·인덱스가 따라가지 않아 쓰지 않는 것을 권장. 대신 새 테이블에 같은 컬럼 이름을 규칙으로 적용하고, `수정일시`는 공통 트리거 함수 하나로 자동 갱신, `수정자`는 API가 채운다. 쌓기만 하는 테이블(`reviews`, `assignment_history`, `model_runs`)에는 수정 컬럼을 두지 않는다. 기존 테이블에 소급할지는 구현 ① 때 결정.

### GPU 메모 (개발 PC: RTX 4060 Ti 16GB)
이상 탐지·분류 CNN/ViT급은 충분. 7B급 멀티모달은 양자화해야 가능. 실제 모델 확정 후 재산정 필요. 이미지 디코딩/디스크 읽기도 병목이 될 수 있다. 워커는 컨테이너 밖에서 직접 실행하는 편이 GPU 설정이 간단하다.

### 1단계 구현 메모 (2026-11-02)
- **마이그레이션**: `db/migrations/NNN_*.sql`을 `backend/src/migrate.mjs`가 번호순으로 적용하고 `schema_migrations`에 이력을 남긴다. 파일 하나 = 트랜잭션 하나. 새 환경은 `docker compose up -d`(init SQL) 뒤에 `npm run migrate`. 테스트 DB도 같은 방식으로 만든다. init SQL(01, 02)은 건드리지 않고 변경은 모두 마이그레이션으로 쌓는다.
- **001 내용**: `images`에 수신/추론 컬럼 추가(`width`/`height`는 NULL 허용, 단 `DONE`이면 필수 — CHECK), 기존 이미지는 `DONE`·`source_name=file_name`으로 이전, 새 행 기본값은 `PENDING`. `integrations`, `ingest_batches` 신설. 대기 건 조회용 부분 인덱스(`images_pending_idx`).
- **공통 컬럼 소급**: `users`, `rules`, `images`, `assignments`에 `created_by`/`updated_by`/`updated_at` 보강(이미 있는 것은 유지). `updated_at`은 `set_updated_at()` 트리거가 자동 갱신, `updated_by`는 API가 채우며 NULL은 시스템. 제외: 쌓기 전용(`reviews`, `assignment_history`, `model_runs`, `detections`, `verdicts`), 소속 테이블(`assignment_images`), 대체 예정인 `batch_jobs`. 기존 API 코드는 아직 `updated_by`를 채우지 않는다 (3단계 이후 정리).
- **`images.original_path`**: 아직 NOT NULL. 수신 시 현재 파일 위치로 채우고, 파일이 inbox → processing → done으로 옮겨지면 `source_path`와 함께 갱신하는 방식을 2단계에서 정한다.
- **모델 어댑터** (`backend/src/model/`): `contract.mjs`(5장 계약 검증 `validateResult`/`assertValidResult`, 박스가 이미지 밖이면 위반), `mock.mjs`(`createMockAdapter`: 파일 내용 sha256으로 시드를 정해 같은 파일이면 같은 결과). 인터페이스는 `adapter.modelVersion`, `adapter.infer({imageKey, fileName, filePath, outputDir}) → 계약 객체`, 실패는 예외. `scripts/generate-mock.mjs`는 그대로 두었다 (이미 적재된 3천 장의 재현성 유지).
- `scripts/load-results.mjs`는 새 기본값(PENDING) 때문에 `ingest_status='DONE'`, `source_name`을 명시해서 넣는다.

### 2단계 구현 메모 (2026-11-02)
코드는 `backend/src/ingest/`, 워커 진입점은 `backend/src/worker.mjs`(`npm run worker`), 테스트는 `test/ingest.test.mjs`.
- **폴더 구조**: 허용 루트(`INGEST_ROOT`, 기본 `<FILES_DIR>/ingest`) 아래에 `inbox`(감시) → `processing`(수신되어 처리 대기·처리 중) → `done` / `failed`. 루트를 FILES_DIR 아래에 둬서 완료 파일을 파일 API로 서빙한다(②에서 이미지 ID 기반으로 바뀌어 inbox·failed 파일은 URL로 받을 수 없다).
- **`scanOnce({pool, integration, root, filesDir, seen})`**: 일반 파일 + 허용 확장자만 후보(`lstat`이라 심볼릭 링크 제외). `seen`(호출자가 유지하는 Map)에 직전 `크기:수정시각`이 같으면 안정으로 보고 수신 → 첫 관찰 때는 기억만 한다(=최소 2회 스캔). 수신 순서: 크기 상한·빈 파일·매직바이트 검사 → sha256 → 한 트랜잭션에서 images INSERT(임시 키) → `rcv_<id 6자리>`로 키 확정 → 파일 이동 → COMMIT. 이동 실패면 행도 롤백, COMMIT 실패면 파일을 되돌린다. 검사 불합격은 `failed`로 옮기고 `FAILED` 행을 남긴다(수신 시도를 기록으로 보이게). 같은 해시는 항상 **처음 수신 행**을 `origin_image_id`로 가리킨다(사슬 아님).
- **`processOne({pool, adapter, root, filesDir, ruleName})`**: `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1)`로 한 건을 PROCESSING으로 집는다(오래된 수신 순). 성공: `model_runs`(모델 버전·처리 시간), `detections`, `verdicts`(규칙은 rules의 활성 최신 버전, `rule_id` 기록)를 저장하고 파일을 `done`으로 이동, 크기를 채워 DONE. 실패(어댑터 예외, 계약 위반, imageId 불일치, 파일 없음): `failed`로 이동 + FAILED + 사유(500자), 모델 결과는 저장하지 않음. 배치 카운터(`processed_count`, `failed_count`)를 올리고 전부 끝나면 `finished_at`. 활성 규칙이 없거나 연계 설정을 못 읽는 것은 이미지 탓이 아니므로 이미지를 PENDING으로 두고 예외를 올린다.
- **`runCycle`**: 켜진 FOLDER 연계마다 `scanIntervalSec`이 지났으면 스캔(연계 하나의 오류는 `errors`에 모으고 다른 연계·추론을 막지 않음) → 대기 이미지를 `maxPerCycle`(기본 20)장까지 처리. 시각은 `now` 인자로 받아 테스트에서 시간을 흉내 낸다. 워커는 시작 시 `recoverStuck`(PROCESSING → PENDING)을 1회 하고, 연계가 하나도 없으면 기본 폴더 연계를 만든다. SIGINT/SIGTERM에는 진행 중인 1장까지만 마치고 종료.
- **설정**: `INGEST_ROOT`, `RULE_NAME`(기본 score-threshold), `MODEL_ADAPTER`(기본 mock, `src/model/index.mjs`). 연계 폴더 설정은 `folder-config.mjs`가 검증한다(절대 경로·루트 이탈·폴더 중복 거부).
- **알려진 한계**: 실패 건 재시도와 설정 변경 이력은 연계 관리 화면 단계에서 다룬다. 새로 수신·추론된 이미지는 아직 신규 배정 조건(`ingest_status='DONE'`)이 명시되어 있지 않다(⑥에서 명시). 스캐너 중복과 고아 파일은 아래 "워커 단일 실행과 시작 시 정리"로 해소했다.

### 워커 단일 실행과 시작 시 정리 (2026-11-02, ①)
- **결정**: 워커는 하나만 실행한다. 폴더당 워커 1개가 일반적인 구성이고, 사고로 둘이 뜨는 경우(실행해 두고 잊음, 재시작 겹침)를 막는 것이 목적이다.
- **방식**: `ingest/lock.mjs`가 PostgreSQL advisory lock(`pg_try_advisory_lock(hashtext('qa-review:ingest-worker'))`)을 잡는다. 못 잡으면 안내 후 종료 코드 1. 잠금은 DB 연결에 묶여 프로세스가 죽거나 연결이 끊기면 DB가 자동으로 푼다(잠금 파일의 찌꺼기 문제 없음). 잠금을 쥔 연결은 워커가 끝날 때까지 풀에 돌려주지 않으며, 연결이 끊겨 잠금을 잃으면 `onLost`로 알려 워커가 멈춘다(다른 워커와 겹치지 않게).
- **범위**: 워커 전체에 잠금 하나(모든 폴더 연계를 한 워커가 담당 → 폴더마다 스캐너 1개가 함께 보장됨). 폴더별 워커 분리가 필요해지면 키를 연계 id로 나눈다.
- **순서가 중요**: 잠금을 잡은 뒤에 정리 작업을 한다. 잠금 없이 정리하면 다른 워커가 처리 중인 `PROCESSING` 건을 대기로 되돌려 같은 이미지가 두 번 추론된다.
- **시작 시 정리** (`ingest/recover.mjs`, 시작 시 1회): (1) `PROCESSING` → `PENDING`. (2) `processing` 폴더의 파일 이름(= image_key)을 한 번의 쿼리(`= ANY`)로 DB와 대조해, 행이 없는 파일(수신 중 이동 직후 COMMIT 전에 죽은 고아)을 감시 폴더로 되돌려 다음 스캔에서 다시 수신한다. 단일 워커 + 시작 시점이라 수신 도중인 파일이 없으므로 "오래된 파일만" 같은 시간 조건이 필요 없다. 감시 폴더에 같은 이름이 있으면 덮어쓰지 않고 `-2`를 붙인다. 폴더 부재/설정 오류는 그 연계만 오류로 기록한다. 3천 장에서도 쿼리 1회.
- 주기적 점검 방식(워커 실행 중에도 고아를 찾기)은 보류. 고아는 드문 사고이고 시작 시 정리로 충분하다고 판단했다. 필요해지면 "DB에 행이 없고 수정 후 N분 경과" 조건으로 `runCycle`에 추가한다.

## 9. 결정: 파일 접근, 원본/미리보기, 생성 이미지, 검수자 표시 (2026-11-02, 구현 예정)

### 파일 접근을 이미지 ID 기반 API로 (②)
- **문제**: 지금 `/files/<경로>`는 디스크 폴더 구조를 그대로 URL에 노출하고 권한이 "로그인 여부"뿐이다. `data/images/ingest/inbox`, `failed`(검증 전·불합격 파일)도 이름을 알면 로그인한 누구나 받을 수 있다.
- **결정**: 경로 대신 이미지 ID로 요청한다. 서버가 DB에서 파일 위치를 찾아 내려주므로 URL에서 경로 추측·`../` 우회가 불가능하다.
  `GET /api/images/:imageKey/thumb | preview | original | heatmap`
- **권한**: 관리자는 전부, QA 담당자는 자기에게 배정된 배정에 속한 이미지만. `ingest_status='DONE'`이 아닌 이미지는 거부. 요청마다 인덱스 쿼리 1회(`assignment_images(image_id)` 인덱스 존재). 구현 뒤 3천 장에서 실제 지연을 재 본다.
- **헤더**: `Cache-Control: private` + `ETag`(정적 서빙이 자동으로 주던 캐시 헤더를 직접 붙여야 한다. 빼먹으면 이미지를 볼 때마다 전체를 다시 받는다), `X-Content-Type-Options: nosniff`, SVG는 직접 열었을 때 스크립트가 돌지 않도록 `Content-Security-Policy: sandbox`. 원본은 스트림으로 전송(큰 파일을 메모리에 올리지 않음).
- **사본이 없을 때**: `thumb`/`preview`가 아직 없으면 원본으로 대신 내려준다(생성 단계 전 호환). 기존 `/files`는 제거하고 목 이미지·히트맵도 같은 API로 서빙한다. 이미지 목록 응답의 `thumbUrl/previewUrl/heatmapUrl`을 새 주소로 바꾼다.
- **원본 열람 기록은 만들지 않는다**(사용자 결정). 중요한 기록은 검수 저장 시점이다.

### 원본/미리보기/썸네일 (④, ⑤)
| 종류 | 용도 | 비고 |
|---|---|---|
| thumb | 목록 | 작은 webp. 토글과 무관하게 항상 썸네일 |
| preview | 검수 화면 | 줄인 webp(긴 변 약 2560px 후보). **비율 유지 필수** (박스 좌표는 원본 픽셀 기준이라 잘라내거나 여백을 넣으면 오버레이가 어긋난다) |
| original | 정밀 확인 | 원본 그대로. 판정은 항상 원본 기준 |
- **검수 화면 보기 모드 토글**: `미리보기`(기본) / `원본 고정`. 원본 고정에서는 현재 이미지의 다음 1~2장을 미리 받는다(전체를 받지 않음). 이미 본 것은 브라우저 캐시. 모드는 브라우저 저장(사용자 편의 설정). 추후 후보: 미리보기에서 확대(줌)할 때만 원본으로 교체. 사본은 `processOne`이 추론 후 `thumb_path`/`preview_path`를 채우는 방식(`sharp` 도입 예정, 포맷·변환 정책은 기획서 10장 질문이라 확정 전).

### 검수자·시각 표시 (⑤)
- 데이터는 이미 있다: 검수 저장 시 `reviews`에 행 추가(검수자는 로그인 정보, 시각은 DB 시각), API 이미지 응답에 `reviewerName`/`reviewedAt`. **화면의 검수 패널이 아직 표시하지 않을 뿐**이다. "마지막 검수: 김검수 · 11-02 14:03"을 표시하고 번복 이력(한 이미지의 변경 기록) 보기를 후보로 둔다.
- `images` 행을 UPDATE해 검수자를 덮어쓰는 방식은 채택하지 않는다: 재점검으로 같은 이미지가 여러 배정에 들어갈 수 있고, 덮어쓰면 번복 이력과 소요 시간 분석이 사라진다. 현재의 "쌓기만 하는 reviews + 최신 행이 현재 상태"를 유지한다.

## 9. 결정: 사용자·권한·메뉴 관리 (2026-11-04, 1단계 구현 완료)

### 확정된 결정
- **권한 3종**: 관리자(`admin`), 연구원(`researcher`), QA(`qa`). 연구원은 화면을 보고 확인할 수 있고, **이미지 파일을 업로드해 수신 폴더에 올릴 수 있어야 한다**(업로드 기능은 별도 설계 필요: 크기·형식·저장 위치, 수신 연계와의 연결). 권한 종류는 이후 늘 수 있으므로 코드의 `CHECK (role IN ...)`가 아니라 **DB 테이블로 관리**한다.
- **계정 상태**: `PENDING`(가입 승인 대기) / `ACTIVE`(사용 중) / `EXPIRED`(사용 기한 만료) / `DISABLED`(관리자가 비활성화). 상태는 영문 코드, 한글은 화면에서 매핑.
- **만료는 사용 기한 만료**: `expires_at`을 관리자가 임의로 설정할 수 있고, **로그인할 때마다 로그인 시점 + 1년으로 갱신**해 장기 미사용자의 접근을 막는다. 만료된 사용자는 **만료 해제 요청**을 보낼 수 있고, 이는 계정 상태를 바꾸는 요청이다(요청 이력 필요).
- **가입 시 권한 신청**: 가입 폼에 신청 권한(`requested_role`)을 받고, 관리자가 승인할 때 신청대로 줄지 다른 권한을 줄지 정한다. 신청 권한과 부여 권한을 따로 저장한다.
- **화면 구성**: ① **사용자 관리** — 조회 조건(상태 라디오: 전체/가입 승인 대기/사용 중/만료/비활성, 권한 콤보박스, 이름·이메일 검색), 목록, 수정 모달(승인·반려, 권한 변경, 비활성화·재활성화, 만료일 설정, 비밀번호 초기화). **가입 승인과 만료 해제 요청은 같은 화면(같은 섹션)에서 보되 상태 필터에 따라 보이는 항목과 버튼을 다르게** 한다(승인 대기: 신청 권한, 승인·반려 / 만료: 만료일, 해제 요청, 해제). ② **권한별 메뉴 관리** — 권한(행) × 메뉴(열) 체크 표.
- **로그인 안내**: 승인 대기·만료·비활성은 구분해서 안내한다("승인 대기 중입니다" 등). 계정 존재 여부를 노출하지 않도록 **비밀번호가 맞을 때만** 상태를 알려 준다.
- **권한·메뉴는 DB로 관리**하고, 메뉴 제한은 화면에서 숨기는 것만으로 부족하므로 **API도 같은 권한표로 검사**한다.

### 규모 점검 (현재 코드 기준)
- 권한 비교는 백엔드 약 17곳(대부분 `isAdmin()` 한 함수 경유)과 프론트 약 9곳(`role === 'admin'`)이다. 갈아엎는 수준이 아니라 `isAdmin()`을 권한 코드 기반 검사(`can(user, '...')`)로 바꾸는 작업이다. 가장 큰 일은 메뉴 정의를 `menu.ts`에서 DB로 옮기고 서버가 메뉴 트리를 내려주게 하는 것.

### 3단계 API 구현 메모 (마이그레이션 007)
- **권한 판단의 단일 근거는 `role_permissions`(권한 × 권한 코드)**. 코드에는 "관리자인가"가 아니라 "이 권한 코드가 있는가"만 쓴다(`src/permissions.mjs`의 `can`, `requirePermission`, `requireAnyPermission`). `authenticate`가 요청마다 DB에서 권한 코드를 읽으므로 표를 바꾸면 로그인 중인 사용자에게도 다음 요청부터 적용된다.
- 권한 코드는 두 종류. MENU: 메뉴 하나에 하나씩(`dashboard.view`, `assignment.view`, `my_assignment.view`, `history.view`, `image_list.view`, `model_run.view`, `monitoring.view`, `rule.manage`, `integration.manage`, `user.manage`, `menu.manage`). FUNCTION: 메뉴와 별개의 동작(`assignment.manage` 배정 만들기·확인 완료·남의 배정 처리, `image.view_all` 배정 밖 이미지 열람, `image.upload` 업로드·준비 중).
- 메뉴는 `menus` 테이블(상단/중메뉴/소메뉴/순서/경로/권한 코드)에 있고 `/api/menus/mine`이 내 권한으로 볼 수 있는 트리만 돌려준다. 권한 코드가 있어야 그 메뉴의 API도 쓸 수 있다 (규칙·연계·사용자·모니터링은 각 코드, 배정 API는 `assignment.view` 또는 `my_assignment.view`). 아직 화면이 없는 메뉴(대시보드 등)의 코드는 표에만 있다.
- 기본 부여: 관리자 = 전부, 연구원 = 보기 메뉴 + 모델 실행 이력 + `image.view_all` + `image.upload`, QA = 보기 메뉴(대시보드·배정·내 배정·점검 이력·이미지 목록).
- `PUT /admin/roles/:code/permissions`는 한 권한의 코드 전체를 교체한다(표에서 고친 것을 한 번에 저장). 바뀐 항목만 `permission_history`(GRANT/REVOKE)에 남긴다. **관리자는 `user.manage`·`menu.manage`를 뺄 수 없다**(409) — 아무도 설정을 못 바꾸게 되는 것을 막는다.
- `users.role`은 `roles` 참조(FK)다. 권한 종류를 DB에서 늘릴 수 있게 되었지만, 권한 추가 화면과 `account.mjs`의 `ROLES`(검증용 고정 목록)·프론트 `ROLE_LABEL`은 아직 고정이라 **권한 종류 추가는 후속 과제**.
- `/auth/me`·로그인 응답에 `permissions`(코드 배열)가 들어간다. 프론트의 `role === 'admin'` 비교(약 8곳)는 화면 커밋에서 이것으로 바꾼다.

### 권한 종류 DB 전환 (마이그레이션 008)
- 코드에서 권한 목록(`ROLES`, `SIGNUP_ROLES`)을 없애고 `roles` 테이블이 정한다. 서버는 권한 코드를 DB로 검증한다(`assertRole`): 사용자 수정·승인의 권한 지정은 roles에 있는 값, 가입 신청은 `roles.signup_selectable`이 true인 값(관리자는 false). 새 권한은 `roles`에 한 줄 넣으면 권한 표의 열, 가입·승인·수정·필터에 코드 변경 없이 나타난다(테스트로 보장).
- `GET /api/auth/signup-roles`(로그인 전, 신청 가능 권한)과 `GET /api/roles`(로그인 후, 전체)를 화면의 이름 표시·선택지에 쓴다. `users.requested_role`도 roles 참조(FK)로 바꿨다.
- 코드에 남은 값은 목록이 아니라 기본값 `DEFAULT_ROLE = 'qa'` 하나뿐(가입 직후의 최소 권한, 신청이 없을 때의 기본 신청 권한). 권한 추가·이름 변경은 「권한 관리」 화면이 맡는다(아래 "권한 관리" 메모). 화면은 `useRoles()`(`GET /roles`)로 이름·선택지를 받고, 가입 화면은 `GET /auth/signup-roles`를 쓴다. 권한별 메뉴 표는 상단 다중 선택 필터로 권한 열을 골라 볼 수 있고(숨긴 열의 변경도 저장에 포함), 권한이 많으면 가로 스크롤하되 첫 열(메뉴 이름)은 고정한다. **아직 남은 고정값**: 상단 배지 색(`admin`) 하나. (신규 배정의 담당자 후보는 기능 권한 `assignment.receive`(배정받기)로 바꿨다 — 마이그레이션 011, `GET /assignees`, 서버도 배정 생성 때 같은 기준으로 검사. 새 권한을 만들고 권한별 메뉴에서 '배정받기'를 켜면 코드 변경 없이 후보가 된다.)

### 권한 관리 (마이그레이션 009)
- **삭제 정책(결정)**: 연쇄 삭제(cascade)는 쓰지 않는다. 권한을 지우면 그 권한의 사용자 계정·승인 이력·메뉴 허용 이력이 함께 사라지거나 끊기고, 이 프로젝트는 "누가 무엇을 했는지" 기록을 남기는 것이 원칙이기 때문이다. 기본은 **「사용 안 함」(`roles.is_active=false`)**: 새 가입 신청·승인·권한 변경의 선택지에서 빠지고(`assertRole`이 400), 이미 그 권한을 가진 사용자는 그대로 쓰며 현재 권한 유지 저장도 허용한다. 언제든 다시 켤 수 있다. **진짜 삭제**는 사용자 0명 + 변경 이력(권한 수정, 메뉴 허용 변경)이 없을 때만(잘못 만든 권한 바로잡기용). 시스템 권한(관리자)은 사용 안 함·삭제·가입 신청 가능 여부 변경 불가.
- `roles.description`(nullable) — 「권한 관리」 화면과 「권한별 메뉴」 표 열 머리 툴팁에서만 보인다(`/roles`, `/auth/signup-roles`에는 내려주지 않음). 툴팁은 짙은 말풍선이 표를 가리지 않게 옅은 배경+테두리(`TooltipContent light`).
- API(`role.manage`): `GET/POST /admin/roles`, `GET/PATCH /admin/roles/:code`, `POST /admin/roles/:code/(de)activate`, `DELETE /admin/roles/:code`. 변경은 `role_history`(삭제된 뒤에도 남도록 FK 없음). 코드는 만든 뒤 못 바꾼다. 새 권한은 `role_permissions`가 비어 메뉴 접근이 없는 상태로 시작. 메뉴 `/settings/roles`(사용자 관리 다음), `role.manage`는 관리자에게서 뺄 수 없게 잠금.
- 화면: 리스트(상태 칩·검색·공통 페이징)와 신규/수정 **통합 모달**(수정에는 사용 현황·변경 이력, 하단 좌측에 사용 안 함/삭제). 사용 안 함 권한은 사용자 수정·일괄 승인의 선택지에서 빠지고, 이미 가진 사용자 표시에는 계속 쓴다(`useRoles().activeRoles`).

### 2단계 화면 구현 메모
- 목업 확정 후 구현. 상태 필터(칩)에 따라 열이 바뀌고(승인 대기: 신청 권한·신청일 / 만료: 만료일·마지막 로그인·해제 요청 …), 일괄 처리 버튼도 상태별로 정해진다(`lib/users.ts`의 `bulkActionsFor`). 전체 보기에서는 상태가 섞여 있어 일괄 처리를 숨긴다.
- 선택은 필터·페이지가 바뀌면 비운다(보이지 않는 사용자를 처리하는 실수 방지). "조건에 맞는 전체 N명"은 1000건씩 id만 모아 선택하고, 처리할 때 100명씩 끊어 순서대로 호출해 결과를 합친다.
- 가입 화면에 소속·연락처(선택), 로그인 화면에 만료 해제 요청 버튼(서버가 `code: EXPIRED`를 줄 때만) 추가.

### 2단계 API 구현 메모 (마이그레이션 006)
- `user_profiles`(업체·부서·직급·연락처·업체 주소, users와 1:1)와 `user_history`(SIGNUP/APPROVE/REJECT/ENABLE/DISABLE/EXPIRE/EXPIRY_REQUEST/EXPIRY_RELEASE/ROLE/EXPIRES/PROFILE/PASSWORD_RESET). 프로필 항목은 `account.mjs`의 `PROFILE_FIELDS`와 마이그레이션만 고치면 늘릴 수 있다. 가입 폼의 프로필은 모두 선택 항목.
- 관리자 API는 `/api/admin/users` (목록·상세·수정·`bulk`·`reset-password`). 처리는 모두 `bulk` 하나로 한다: `APPROVE`(신청 권한대로, 또는 `role` 지정) / `REJECT` / `DISABLE` / `ENABLE` / `RELEASE_EXPIRY`. 한 번에 최대 100명, 대상이 아닌 사용자(이미 처리됨·본인·없음)는 건너뛰고 사유를 돌려준다. 활성화(승인·재활성·만료 해제)는 사용기한을 오늘 + 1년으로 새로 잡는다.
- 반려는 가입 기록을 남기기 위해 삭제하지 않고 `DISABLED`로 둔다(이력 `REJECT`). 같은 이메일로 다시 가입하려면 관리자가 재활성화한다.
- 만료된 사용자의 기한을 미래로 수정하면 해제로 본다. 사용 가능한 관리자가 0명이 되는 처리(강등·비활성)는 통째로 취소(409). 본인 계정은 일괄 비활성·반려에서 건너뛴다.
- 만료 해제 요청(`POST /auth/expiry-release-request`)은 이메일·비밀번호를 다시 받아 본인 확인 후 요청 시각만 남긴다(상태는 그대로, 해제는 관리자). 임시 비밀번호는 10자 무작위를 한 번만 응답하고 이력에는 남기지 않는다. 이메일 발송과 비밀번호 변경 강제는 아래 "임시 비밀번호 메일과 변경 강제"에서 구현.

### 공통 규칙: 목록 페이징 (2026-11-04)
- 모든 목록(게시판)은 기본 20건, 하단 **좌측 콤보박스**로 20/50/100/1000건 중 선택한다(크기를 바꾸면 1쪽으로). 서버는 `pageSize` 최대 1000 (`src/paging.mjs`의 `pagingQuery`를 스키마에 펼쳐 쓴다). 화면은 `Pagination` 컴포넌트 하나를 쓴다. 하단 바는 세 칸: 좌측 = 총 건수·크기 콤보, **가운데 = 번호 이동**(현재 페이지가 속한 10개 묶음만 표시, « ‹ › » 로 처음/이전/다음/끝), 우측 = `현재 / 전체 쪽`.

### 실제 모델 검토와 PatchCore 연결 (2026-11-04)
- **후보**: Anomalib(코드 Apache-2.0)의 PatchCore 먼저(학습이 단순: 정상 이미지의 패치 특징을 메모리 뱅크에 저장, 이상 점수·이상 맵을 낸다). EfficientAD는 그 다음. MVTec AD는 CC BY-NC-SA라 쓰지 않는다.
- **환경**: RTX 4060 Ti 16GB, Python 3.12 있음, torch·anomalib 미설치(설치 시 CUDA torch 수 GB). 백엔드는 Node(sharp)라 모델은 **별도 Python 프로세스**로 두고 Node 어댑터가 호출한다(ONNX 내보내기는 PatchCore의 메모리 뱅크 검색 때문에 번거로워 제외).
- **데이터**: `data/images/real` 300장 = 정상 203 + 결함 97(`ground_truth.jsonl`에 박스). 정상 중 일부로 학습, 나머지 정상 + 결함으로 평가. 주의: 이 이미지는 장면·각도가 다양한 생성 이미지라 "같은 물건을 같은 자세로 찍은 공장 이미지"를 가정하는 PatchCore에 불리하다. 성능은 낮을 수 있고, 지금은 품질 판단이 목적이 아니라 **어댑터 연결이 목적**이다.
- **계약과의 간극(결정 필요)**: ① 점수는 0~1이어야 하는데 PatchCore 원점수는 상한이 없다 → 정상 검증 이미지의 분포로 0~1 정규화하고, 정규화 기준을 모델 버전에 묶어 기록(판정 임계값은 계속 `rules`). ② 박스: 이상 맵을 임계로 잘라 연결 영역의 외접 박스를 만들고 **원본 픽셀**로 환산(후처리). ③ `reasonCode`: PatchCore는 원인을 구분하지 못한다 → **결정: 계약에 `UNKNOWN`(원인 미분류)을 추가**(마이그레이션 010, 화면 표시 '원인 미분류'). 원인을 지어내 채우지 않는다. 목 모델은 기존 6개 원인만 계속 쓴다(`CAUSE_CODES`). ④ 히트맵 PNG는 Python이 만든다.
- **연결 방식(제안)**: `backend/src/model/patchcore.mjs`(어댑터, `MODEL_ADAPTER=patchcore`)가 `python/` 아래의 추론 서버(상주, 모델 1회 로드)에 이미지 경로를 보내고 5장 JSON을 받는다. 어댑터는 기존처럼 `assertValidResult`로 검사. `modelVersion = patchcore-<백본>-<학습 데이터 해시>`.
- **라이선스**: 백본 가중치(wide_resnet50_2, ImageNet 사전학습)의 상업 이용 조건은 미확인(데이터셋 ImageNet의 약관 확인 필요). 연습·비상업 범위에서는 문제 없고, 상업 전환 전에 확인한다. 회사 데이터는 학습·평가에 쓰지 않는다.

#### 구현 메모 (PatchCore 어댑터)
- 구조: `backend/src/model/patchcore.mjs`(어댑터) ↔ stdin/stdout JSON Lines ↔ `python/serve.py`(상주, 모델 1회 로드). 모델 폴더의 `meta.json`이 `modelVersion`·점수 기준·박스 설정을 담고, 서버가 보고한 버전이 meta와 다르면 어댑터가 거부한다(판정 기록이 거짓이 되지 않게). 프로세스 사망·시간 초과는 그 이미지만 실패로 처리하고 다음 요청에서 다시 띄운다. 설정: `MODEL_ADAPTER=patchcore`, 선택 `PATCHCORE_MODEL_DIR`, `PYTHON_BIN`. 자세한 사용법은 `python/README.md`.
- 점수 방향은 기존 규칙과 같다(높을수록 정상). 원점수 → 심각도(정상 검증 점수의 중앙값=0, 95백분위=0.5) → `1 − 심각도`. 이상 맵은 가우시안 평활로 최댓값이 이미지 점수보다 낮아 **기준을 따로**(`mapCalibration`) 둔다 — 처음에 이를 놓쳐 불량(0.26)인데 박스가 하나도 없는 이미지가 나왔고, 기준 분리로 해결했다. 점수 기준·박스 설정이 바뀌면 `modelVersion` 끝의 해시(`-c…`)가 바뀐다.
- 학습은 anomalib의 Lightning 루프를 쓰지 않고 직접 돈다(정상 패치 특징 수집 → `fit()` 코어셋). 입력 320×576(원본 비율 유지에 가깝게; 256×256 정사각 변환은 쓰지 않음). 정상 203장 중 120장 학습(약 4분, RTX 4060 Ti), 83장은 점수 기준용.
- 추론 속도: GPU에서 이미지당 약 0.1초(첫 장은 CUDA 준비로 수백 ms).
- **확인한 것(품질 평가가 아님)**: 정상 3장 + 결함 3장을 워커로 흘려 끝까지 처리됨(DB에 `patchcore-…` 모델 버전, 점수·판정·박스(`UNKNOWN`)·히트맵 PNG 저장). 결함 3장은 판정 DEFECT 1·SUSPECT 1·NORMAL 1, 박스는 정답 영역 안의 작은 박스 1개 — 이 데이터(자세·장면이 제각각인 생성 이미지)에서는 PatchCore 성능이 높지 않을 것이라는 사전 예상과 같다. 체계적 평가(이미지 AUROC, 박스 겹침)와 다른 모델 비교는 필요할 때 `ground_truth.jsonl`로 한다.

### 이미지 업로드 (2026-11-04, API 완료 · 화면은 목업 확인 대기)
- **결정**: 올리는 사람은 `image.upload` 권한(기본: 관리자·연구원). 올린 파일은 **수신 폴더**(켜져 있는 폴더 연계 중 가장 먼저 만든 것의 감시 폴더)에 두고, 이후는 기존 스캔 → 추론 → 판정 흐름이 그대로 한다. 업로드 전용 처리 경로를 따로 만들지 않는다.
- **DB 기록**(마이그레이션 012): `upload_batches`(누가·언제·몇 장 올리려 했나·메모·상태) + `upload_files`(원래 이름, 수신 폴더에 둔 이름 `up<id>__…`, 크기, sha256, RECEIVED/REJECTED+이유, `image_id`). 스캐너가 그 파일을 `images`로 등록하는 순간 `upload_files.image_id`가 채워져 **업로드 → 수신 대기 → 검사 중 → 완료/검사 실패**를 한 줄로 추적한다(`image_id`가 비어 있으면 아직 수신 대기). 업로드 실패(이미지가 아님·확장자·크기 초과·빈 파일)도 이유와 함께 REJECTED로 남는다.
- **수천 장**: 한 번의 업로드를 배치 하나로 묶고(상한 `UPLOAD_MAX_BATCH_FILES`, 기본 10,000장), 파일은 **한 장씩 따로** 전송한다(`PUT /uploads/:id/files?name=`, 본문 = 원본 바이트, 디스크로 스트리밍). 화면이 몇 장씩 동시에 보내며 진행률·재시도를 관리한다. 서버 처리량 확인: 작은 PNG 3,000장을 4개 동시로 약 5.6초(서버 안에서 측정, 네트워크 제외). 한 요청에 수천 장을 담는 방식(multipart)은 쓰지 않는다 — 요청 하나가 실패하면 전부 다시 올려야 하고 메모리·타임아웃 문제가 있다.
- **안전**: 임시 이름(`.part`)으로 받아 검사(확장자·크기·내용 매직바이트)한 뒤 수신 폴더로 옮겨 스캐너가 덜 받은 파일을 집지 않는다. 수신 폴더의 이름은 서버가 정하므로(경로·특수문자 제거) 폴더 밖으로 나갈 수 없고 같은 이름도 충돌하지 않는다. 크기 상한은 연계의 `maxFileMB`를 따른다. 상한을 넘는 본문은 읽어서 버린다(연결을 끊으면 화면이 거절 사유를 못 받음).
- **권한**: `image.upload`는 메뉴 권한이 되어 「데이터 > 이미지 > 이미지 업로드」 메뉴가 생겼다(이전의 '준비 중' 기능 권한에서 승격). 남의 업로드 이력은 기능 권한 `upload.view_all`(기본 관리자)이 있어야 보이고, 없으면 내가 올린 것만 보인다. 배치에 파일을 더할 수 있는 사람은 만든 본인뿐.
- 화면(목업 확인 후 구현): 끌어놓기(폴더는 안쪽까지)·파일/폴더 선택 → 올릴 수 있는 것과 제외할 것(이유) 구분 → 업로드 시작 → 진행률·남은 시간·일시 중지·취소 → 전송 실패만 같은 배치에 다시 시도 → 업로드 이력(올린 사람·처리 현황, 수신 대기/검사 중이 있으면 5초마다 새로 고침)과 파일별 상세. 전송 큐(동시 4장·재시도 2회·중지/취소)는 `lib/upload.ts`의 순수 함수로 분리해 단위 테스트, 진행 상태는 `hooks/useUploader.ts`. 올리는 중 창을 닫으려 하면 브라우저가 확인한다. 150장 시험 업로드가 수신 → 추론 → 완료까지 이어지는 것을 브라우저로 확인했다.

#### 평가 결과 (2026-11-04, `python/evaluate.py`, 모델 `patchcore-wide_resnet50_2-320x576-b149903a-cfcd4`)
평가 대상: 결함 97장 + 학습에 쓰지 않은 정상 83장. (정상 120장으로 학습)
- **이미지 단위 구분력은 약하다**: AUROC **0.683**(0.5=무작위). 컷오프 0.9에서 결함 61.9%를 잡지만 정상 37.3%가 오탐. 컷오프 0.5는 결함 30.9% / 오탐 4.8%. 속도는 이미지당 약 80ms(GPU).
- **결함 종류별 차이가 크다**: SCALE_ANOMALY(비율 이상) AUROC 0.906 / 박스 적중 57~64% — 잘 잡는다. COMPOSITE_EDGE 0.771, TEXTURE_ANOMALY 0.732, LIGHTING_MISMATCH 0.643, SHAPE_DISTORTION 0.632, **PART_COUNT_MISMATCH 0.563(거의 무작위)**. 부품 개수·형태 같은 "의미" 이상은 패치 특징 거리로는 구분되지 않는다.
- **위치는 거의 못 맞춘다**: IoU≥0.1 기준 정답 박스 10.6%(박스 기준을 0.35로 낮춰도 12.8%, 오탐 박스 증가). 병목은 박스 후처리가 아니라 모델의 변별력이다. 픽셀 단위 AUROC 0.837은 이상 맵이 정답 영역 쪽으로 어느 정도 쏠린다는 뜻.
- **해석**: 사전 예상대로 자세·장면이 다양한 생성 이미지에는 PatchCore가 맞지 않는다. 지금 값은 "연결 검증용 기준선"이다. 개선 후보(필요할 때): ① 같은 구도의 이미지로 학습 데이터를 좁히기 ② 입력 해상도·코어셋 비율 조정 ③ 다른 모델(EfficientAD 등)을 같은 `metrics.py`로 비교 ④ 결함 박스 정답이 있으므로 지도학습 탐지(라이선스 확인 필요). 판정 규칙 경계값은 이 컷오프 표를 보고 규칙 화면에서 정한다(코드에 넣지 않음).

### 로그인 시도 횟수 제한 (2026-11-05, 마이그레이션 013)
- **방식**: 실패 횟수를 DB(`login_failures`, 기준 `EMAIL`·`IP`)에 둔다. 서버를 다시 켜도 유지되고 서버가 여러 대여도 일관된다. 기본값은 구간 15분 안에 이메일당 5번 / 접속 주소당 30번 실패하면 15분 잠금(`LOGIN_MAX_FAILURES`, `LOGIN_IP_MAX_FAILURES`, `LOGIN_WINDOW_SEC`, `LOGIN_LOCK_SEC`). 코드는 `src/loginGuard.mjs`.
- **응답**: 잠겨 있으면 429 + `code: LOCKED` + `Retry-After` 헤더, 문구는 "N분 후에 다시 시도해 주세요". 화면은 서버 문구를 그대로 보여 주므로 프론트 변경 없음.
- **계정 존재 여부 비노출**: 없는 이메일도 똑같이 세어 같은 순서로 잠근다. 이메일은 대소문자·앞뒤 공백을 무시하고 한 계정으로 센다.
- **잠금 중에는 비밀번호를 검사하지 않는다**(맞는 비밀번호도 거부). 잠금 중 시도는 실패로 세지 않아 잠금이 계속 늘어나지 않는다. 그렇지 않으면 남이 내 이메일로 계속 시도해 나를 영구히 잠글 수 있다.
- **초기화**: 비밀번호가 맞으면(계정 상태가 승인 대기·만료여도) 그 이메일의 실패 기록을 지운다. 주소 기준 기록은 구간이 지나야 풀린다. 비밀번호를 받는 `POST /auth/expiry-release-request`도 같은 횟수를 공유한다.
- **알려진 한계**: 프록시 뒤에 두면 `req.ip`가 프록시 주소가 되어 주소 기준 한도가 모두에게 적용된다 → 운영에서 프록시를 쓸 때 Fastify `trustProxy` 설정이 필요. 관리자가 잠금을 수동으로 풀어 주는 기능은 없다(15분 뒤 자동 해제). 공격자가 남의 이메일로 15분마다 시도하면 그 사용자는 계속 불편하다(이메일 기준의 한계, 주소 기준과 함께 쓰는 이유).

### 임시 비밀번호 메일과 변경 강제 (2026-11-05, 마이그레이션 014)
- **메일 모드** (`MAIL_MODE`, `src/mail.mjs`, nodemailer): `off`(기본, 발송 안 함) / `log`(개발용, 서버 로그에 출력, 운영에서는 시작 시 거부) / `smtp`(실제 발송, `SMTP_*`). 잘못된 값이나 SMTP_HOST 누락은 서버 시작 시 거부한다.

- **발송 기록** `mail_log`: 종류·받는 사람·모드·성공/실패·오류만 남기고 본문은 저장하지 않는다(임시 비밀번호가 들어 있음). 실패 기록은 롤백과 무관하게 남도록 별도 연결로 기록한다.

- **본인 비밀번호 변경** `POST /auth/change-password`: 현재 비밀번호 확인(틀리면 로그인과 같은 횟수 제한에 센다), 새 비밀번호 8자 이상·현재와 달라야 함, 이력 `PASSWORD_CHANGE`. 현재 비밀번호가 틀린 응답은 401이 아니라 400 `WRONG_PASSWORD`(401은 화면이 로그아웃 처리하는 신호이기 때문).
- **알려진 한계**: 비밀번호를 바꿔도 이미 발급된 토큰(최대 12시간)은 만료 전까지 유효하다. 가입 시 비밀번호 길이 기준(4자)은 데모 계정 때문에 그대로다.
- **화면 (2026-11-14)**: `user.mustChangePassword`가 true면 `AppLayout`이 메뉴를 불러오기 전에(서버가 `/menus/mine`도 403으로 막으므로) `ForcePasswordChangePage`만 그린다. 변경 성공 시 스토어의 플래그를 내리면 원래 화면으로 돌아간다. 로그인 중에 관리자가 초기화해 API가 403 `MUST_CHANGE_PASSWORD`를 주면 `client.ts`가 같은 플래그를 올려 변경 화면으로 바꾼다. 입력 검사(8자·현재와 다름·확인 일치)는 `lib/users.ts`의 `validatePasswordChange`(서버와 같은 기준, 서버가 최종 판단). 본인 변경은 상단 `비밀번호 변경`(다이얼로그)으로도 가능. 메일 발송 응답(`{ sent, to }`)이면 사용자 수정 모달은 임시 비밀번호 대신 "메일 발송" 안내만 보여 준다. 이력 문구에 `PASSWORD_CHANGE`와 발송 방식이 추가됐다. ### 배포 구성 (2026-11-14)
- **한 이미지**: 멀티스테이지 `Dockerfile`이 화면(`npm run build`)을 만들고, 실행 이미지에서 API 서버가 `FRONTEND_DIST`의 파일을 `@fastify/static`으로 내려준다. 같은 출처라 쿠키·프록시 설정이 필요 없다. 모르는 GET 경로는 `index.html`(화면 라우터), `/api/*`와 GET이 아닌 요청은 기존처럼 JSON 404. 이유: 컨테이너·호스팅 서비스를 하나로 줄여 "한 줄 실행"과 포트폴리오 공개를 쉽게 하려는 것(화면을 CDN에 따로 올리는 방식은 CORS·쿠키 SameSite를 따로 풀어야 한다).
- **프로필**: `docker-compose.yml`의 `app`·`worker`는 `profiles: ["app"]`. 기존 개발 흐름(`docker compose up -d`는 DB만)을 그대로 두기 위함. 두 서비스는 같은 이미지(`qa-review-app`)를 쓰고 이미지 파일 볼륨(`appdata`)을 공유한다. 마이그레이션은 `app`만 시작 시 적용하고, `worker`는 `app`이 건강해진 뒤에 시작한다.
- **시작 스크립트** `backend/scripts/docker-start.mjs`: 마이그레이션 → `DEMO_DATA_COUNT`>0이고 볼륨에 `results.jsonl`이 없으면 목 데이터 생성·적재(두 번째 시작부터는 건너뜀) → 서버. 셸 스크립트 대신 `.mjs`로 쓴 이유는 윈도우 CRLF가 섞여도 깨지지 않게 하려는 것.

- **데모 모드 (`DEMO_MODE`)**: 로그인 화면의 데모 계정 안내·기본 입력값을 서버 설정으로 켜고 끈다. 화면은 로그인 전에 `GET /api/config`(비밀이 아닌 값만)로 읽는다. 기본값은 운영(`NODE_ENV=production`)이 아닐 때만 켬 — 개발은 그대로, 운영은 안전한 쪽. compose는 로컬 한 줄 실행을 위해 true로 두고, 공개 서버에서 false로 바꾸도록 deploy.md 체크리스트 0번에 둔다. 이유: 빌드 시점 상수로 숨기면 이미지를 다시 빌드해야 하지만 환경변수는 같은 이미지로 로컬 데모와 공개를 모두 처리한다. 한계: 끄더라도 시드 계정 비밀번호(`1234`)는 DB에 남으므로 바꾸는 절차가 필요하다(체크리스트 4번).
- **공개 서버의 초기 비밀번호 (2026-11-14)**: 시드 SQL(`db/init/02_seed.sql`)의 `1234`는 저장소에 공개된 값이라 비밀번호를 복잡하게 바꿔 적어도 소용이 없다(올리면 똑같이 공개). 그래서 값을 저장소에 두지 않고 `.env`의 `ADMIN_PASSWORD`로 받는다(방식 A). `DEMO_MODE=false`면 `docker-start`가 `bootstrap-admin`을 먼저 실행한다(`src/bootstrap.mjs`): 비밀번호가 **아직 1234인 계정**만 대상으로 ① 관리자 → `ADMIN_PASSWORD`로 교체(12자 이상, `1234`·이메일과 같은 값 거부, `ADMIN_EMAIL`이 있으면 이메일도) ② 나머지 → 비활성화 + 무작위 비밀번호(다시 켜도 1234로 못 들어옴). 대상을 '아직 1234인 계정'으로 잡은 이유는 상태 표식을 따로 두지 않고도 멱등이기 때문이다(한 번 바꾸면 더 하지 않고, 관리자가 나중에 바꾼 비밀번호를 재시작이 덮어쓰지 않는다). 설정이 없거나 약하면 **서버가 시작되지 않는다**(실패가 닫히는 쪽). 이력은 `via: BOOTSTRAP`만 남기고 값은 남기지 않으며 출력에도 값이 없다. 로컬 데모(`DEMO_MODE=true`)는 그대로 `1234`. 한계: 컨테이너가 아닌 배포에서는 `npm run bootstrap-admin`을 직접 실행해야 한다(서버 시작 시 자동 검사는 아님).
- **데모 배정** `scripts/seed-demo.mjs`: 배정이 없고 수신 완료 이미지가 있을 때만 `POST /api/assignments`를 호출해 qa1에게 1건을 만든다(두 번째 시작부터는 건너뜀). 새 로직을 만들지 않고 실제 API를 쓰며, 관리자 비밀번호 대신 토큰을 직접 발급하므로 비밀번호가 바뀌어도 동작한다.

### 이미지 확대 보기·박스 호버와 남은 메뉴 화면 4종 (2026-11-14)
- **목업 먼저**: 확대·호버는 Artifact(인터랙티브 목업)로 먼저 보여 주고 추천안으로 확정했다. 내 배정·점검 이력·이미지 목록·대시보드는 기존 목록 화면 규칙(상태 칩·페이징·검색)을 그대로 따르는 화면이라 목업을 생략하고 구현 후 실제 화면으로 확인했다(디자인 규칙 0번의 예외, 기록해 둔다).
- **크게 보기(A안)**: 작은 모달 안에서 키우는 대신 화면 가득 보는 전용 창. 이유는 원본 크기(1:1) 확인과 휠 확대가 작은 결함을 보는 데 필요해서. 열린 상세 모달 위에 **중첩 Dialog**(Base UI)로 띄우고, 이미지가 바뀌면(`key`) 확대 상태를 처음으로 돌린다. 확대 계산은 `lib/zoom.ts`(순수 함수, 커서 기준 확대·1:1 배율·범위 제한)로 빼서 단위 테스트한다. 창 안에서도 승인/반려 가능(다음 미검토로 넘어가는 동작은 검수 화면과 같다). 확대해도 박스 테두리·번호 배지는 같은 크기로 보이게 배율로 나눠 그린다. 확대 화면은 원본 파일을 쓰고 줄인 사본을 밑에 깔아 둔다(원본이 내려오는 동안 빈 화면 없음).
- **박스 호버**: 박스에는 번호 배지만 항상 보이고(이미지를 덜 가린다), 올리면 `BoxTip` 카드(한글 원인·점수 막대·설명·영문 코드·원본 픽셀 위치). 호버 상태는 `hot`(번호) 하나로 박스·오른쪽 목록·카드가 공유한다. 카드 위치는 박스의 DOM 좌표를 재서 스타일에 직접 쓰고(상태를 늘리지 않음) 컨테이너 안에 머물게 한다. **원인 설명 문구 7종은 `REASON_DESCRIPTIONS`(화면 상수)** — 값이 아니라 문구라서 서버·DB에 두지 않았고, 내용은 초안이라 확인이 필요하다.
- **방향키 버그(기존)**: 모달 안에서 탭 버튼에 포커스가 있으면 Base UI 탭이 ←/→를 가져가 검수 화면의 이미지 이동이 동작하지 않았다(E2E가 방향키를 검증하지 않아 못 잡음). 단축키 리스너를 **캡처 단계**로 옮기고 방향키는 `stopPropagation`한다. 크게 보기 창도 같은 방식이며 E2E에 방향키 검증을 넣었다.
- **「모델 실행 이력」 메뉴 제거(015)**: 메뉴·권한 부여·권한 코드(`model_run.view`)를 함께 삭제. `model_runs` 테이블(판정 근거)은 그대로. 이유는 소요 시간 분석의 '모델 처리 시간'과 겹치고 화면이 없었기 때문.
- **내 배정**: 새 화면을 만들지 않고 배정 리스트를 `mine` 옵션으로 재사용 — 서버는 `GET /assignments?mine=true`(목록·건수·검색이 모두 내 것으로 한정), 화면은 신규 배정 버튼만 숨긴다.
- **점검 이력** `GET /api/review-history`: `reviews`가 쌓기 전용이라 번복도 한 줄씩 남는다. 같은 배정·이미지에서 가장 최근 결정이 아니면 `isCurrent=false`('번복됨'). 기본은 내 기록, `scope=all`은 `assignment.manage`가 있어야 한다(없으면 403). 상태 칩 건수는 범위만 반영하고 검색·상태 필터와는 독립.
- **이미지 목록** `GET /api/image-list`·`/image-list/:key`: 수신·판정이 끝난(DONE) 이미지만. **열람 범위는 파일 API와 같은 규칙**(`image.view_all` 권한자는 전부, 그 외는 내게 배정된 것만 — 목록과 상세 모두). 판정 칩의 건수는 판정 필터만 뺀 같은 조건으로 센다. 크게 보기는 `ImageLightbox`를 `browse`(보기 전용)로 재사용해 승인/반려·검수 상태를 숨긴다.
- **대시보드** `GET /api/dashboard?tz=`: 범위가 두 갈래다 — 이미지 분포는 `image.view_all`, 배정·검수 진행·최근 7일은 `assignment.manage`가 전체/내 것을 가른다. 미배정 검수 대상은 배정 관리 권한자에게만 준다. 날짜는 브라우저 시간대(`tz`)로 나누며 형식 검사 + DB가 받아들이는지 확인해 잘못되면 400. 차트는 **단일 계열이라 범례 없이 제목이 이름을 대신**하고, 값은 최대·오늘만 직접 라벨, 막대에 올리면 값 툴팁, `표로 보기`로 같은 값을 표로(색에만 의존하지 않기). 판정 색은 앱 전체 배지 색과 같고 이름·수치를 함께 적는다. 진행률이 반올림하면 0%인데 하나라도 했으면 '1% 미만'으로 표기한다(0%로 보이면 아무것도 안 한 것처럼 읽힘).
- **알려진 한계**: 목 모델의 박스는 가짜(`ground_truth`와 무관)라서 호버 카드의 원인·위치가 실제 결함과 어긋날 수 있다(실제 모델은 `python/evaluate.py`로 정답과 비교). 이미지 목록의 크게 보기는 현재 쪽의 이미지만 넘겨 본다(쪽을 넘기면 닫힘).


### 검수 필터·정렬과 신규 배정 옵션 (2026-11-14)
- **목적**: 검수자가 3천 장을 다 봐야 하는 상황을 줄인다. 두 갈래 — 애초에 배정할 때 볼 필요가 적은 이미지를 덜어내고(정상 표본), 검수 중에는 보고 싶은 것만 걸러 보게(필터·정렬) 한다.
- **정렬 5종** (`src/imageOrder.mjs`, 무작위는 사용자 결정으로 제외): 점수 낮은 순 / 점수 높은 순 / **경계에 가까운 순** / 이상 영역 많은 순 / 최신 수신순. 검수 화면에는 `position`(배정 시 정한 순서)이 더해진 6종. 경계 거리는 `LEAST(|점수-normalMin|, |점수-suspectMin|)`이고 기준값은 **그 판정을 내린 규칙의 `rules.params`**를 쓴다(`latestVerdict`가 `rule_id`를 함께 주고 `RULE_OF_VERDICT`로 잇는다) — 규칙을 새 버전으로 바꿔도 이미 내린 판정의 거리가 소급해서 바뀌지 않는다. 같은 값끼리는 번호로 정해 순서가 흔들리지 않는다.
- **거르기와 정렬은 별개의 컨트롤**: 결과 칩과 판정 콤보박스는 거르기, 정렬은 콤보박스 하나를 더 둔다(이미지 목록 화면과 같은 구성).
- **정상 표본**: `normalPercent`(1~100, 기본 100 = 전부). 후보 중 정상만 `ORDER BY random() LIMIT k`로 뽑고 의심·불량은 전부 후보에 넣은 뒤, 고른 순서로 정렬해 이미지 수 상한으로 자르고, 그 순서를 `assignment_images.position`으로 고정한다. 장수 `k = round(후보×비율)`, 후보가 있으면 최소 1장(`sampleSize`, 화면과 서버가 같은 식). 표본·순서 기준은 `assignment_history`의 문구("정상 표본 5% (104장)", "검수 순서: 경계에 가까운 순")로 남겨 나중에 설명할 수 있게 한다. **기존 배정은 그대로**이고 새 옵션은 새 배정에만 적용된다. 한계: 상한이 정렬 순서대로 자르므로 정렬에서 뒤에 오는 정상 표본이 상한에 잘릴 수 있다(예: 점수 낮은 순에서 정상은 맨 뒤) — 미리보기의 "상한으로 N장만 담깁니다" 문구가 이를 알려 준다. 표본 추출은 매번 새로 무작위(재현용 시드 없음).
- **검수 화면 서버 API**: `GET /assignments/:code/images`에 `sort`·`filter`·`verdict`, `GET /assignments/:code/image-counts`(결과 칩 건수, 판정 필터만 반영), `GET /assignments/:code/next-unreviewed`가 **같은 `FROM`·`WHERE`·정렬을 공유**한다. `next-unreviewed`는 지금 보는 목록 안의 1-based 위치(`row_number`)를 돌려주므로 기본값(필터 없음, 배정 순서)에서는 예전의 `position`과 같다.
- **목록이 흔들리지 않게(목업과 다른 점)**: 목업은 '미검토' 필터에서 결정한 이미지가 목록에서 사라진다고 보여 줬지만, 구현은 **결정한 이미지가 표시만 바뀌고 남는다**. 이유는 낙관적 업데이트와 50장 단위 가상 스크롤 캐시를 함께 쓰는 구조라, 목록에서 즉시 빼면 쪽 경계의 항목이 밀려 어긋나고 A/R 키를 빠르게 누를 때 같은 이미지를 두 번 결정할 위험이 있어서다. 결과 칩 건수(`image-counts`)만 결정 직후 새로 받고, 목록은 필터·정렬을 바꾸거나 다시 열 때 갱신된다.
- **E2E 데이터 공유**: 시나리오들이 같은 테스트 DB의 미배정 이미지를 쓰므로, 새로 배정하는 시나리오는 시작할 때 `freeImages`(테스트 서버에만 있는 `POST /api/__e2e/free-images`, `backend/test/e2e-server.mjs`)로 배정을 비운다. 앱 코드에는 이 경로가 없다.

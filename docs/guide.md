# 사용 가이드: 지금까지 구현된 것과 사용 방법

> 마지막 갱신: 2026-11-04. 설계 이유는 [design.md](design.md), 진행 현황·다음 할 일은 [progress.md](progress.md), 개념 설명은 [study-notes.md](study-notes.md).

## 1. 이 프로젝트가 하는 일

AI가 만든 이미지를 **모델이 먼저 검사(사전 검증)** 하고, **QA 담당자가 화면에서 승인/반려**하는 검수 시스템의 연습용 미니 프로젝트다.

```
이미지 파일 ─→ [수신 워커] ─→ 모델 추론(점수·이상 영역 박스) ─→ 판정(정상/의심/불량)
                                                                      │
관리자: 의심·불량을 골라 담당자에게 배정 ◀──────────────────────────────┘
QA 담당자: 점검 시작 → 이미지 한 장씩 승인/반려 → 점검 완료
관리자: 확인 완료 · 소요 시간 분석 보기
```

**규칙**: 회사 데이터·자료는 절대 쓰지 않는다. 연습 데이터는 직접 만든 것만 쓴다(목 데이터, ComfyUI로 만든 이미지).

## 2. 구성

| 폴더 | 내용 |
|---|---|
| `frontend/` | 화면. React + Vite + TypeScript + Tailwind + shadcn/ui |
| `backend/` | API 서버(Fastify), 수신 워커, 이미지 생성·적재 스크립트 |
| `db/` | `init/` 최초 스키마·시드, `migrations/` 이후 변경 SQL |
| `docker-compose.yml` | PostgreSQL 16 컨테이너 |
| `data/images/` | 이미지·히트맵·사본 (git 제외). 생성 이미지는 `real/`, 수신 폴더는 `ingest/` |
| `docs/` | 기획서(plan), 설계(design), 학습 노트, 이 문서 |

프로세스는 최대 네 개가 따로 돈다: **DB**(Docker), **API 서버**, **프론트 개발 서버**, (선택) **수신 워커**.

## 3. 구현된 기능

### 화면 (프론트엔드)
- 로그인/회원가입, 라이트/다크 테마. **가입은 승인 신청**이다: 신청 권한(QA/연구원)을 고르면 `승인 대기`로 만들어지고 바로 로그인되지 않는다. 승인은 관리자 화면(설정 > 사용자 > 사용자 관리)에서 한다(7-3 참고). 로그인 시 상태별 안내(승인 대기/만료/비활성)는 비밀번호가 맞을 때만 나오고, 로그인할 때마다 사용기한이 1년 뒤로 갱신된다. 이미 받은 로그인 토큰도 비활성·만료되면 바로 막힌다.
- **배정 목록**: 상태별 건수 카드, 상태 필터·검색, 페이지 이동
- **신규 배정**(관리자): 담당자·마감일·대상 AI 판정(정상/의심/불량)·이미지 수와 함께 **검수 순서**와 **정상 표본 비율**을 고른다. 의심·불량은 고른 만큼 전부 대상이고, 정상을 켜면 `정상은 표본만`(기본 5%)이 나타나 정상 중 무작위 일부만 담긴다(후보가 있으면 최소 1장). 이미지 수보다 많으면 고른 **검수 순서대로 잘라** 담는다. 순서는 점수 낮은 순(기본)·점수 높은 순·경계에 가까운 순(정상/의심 0.90, 의심/불량 0.50 같은 기준점에 가까운 애매한 것부터)·이상 영역 많은 순·최신 수신순. 정한 순서와 표본 기준은 배정 이력에 남는다
- **배정 상세**: 단계 표시(배정 → 점검중 → 점검완료 → 확인완료), 개요, 점검 내용 메모, 상태 변경 이력
- **이미지 검수**: 3천 장도 부드럽게(서버 페이지네이션 + 가상 스크롤 + 낙관적 업데이트)
  - 이미지 위에 **이상 영역 박스**와 **히트맵** 겹쳐 보기(둘 다/히트맵/박스/끄기, 투명도 조절)
  - **필터·정렬**(목록 위): 결과 칩(전체·미검토·승인·반려, 건수 표시) + `AI 판정` 콤보박스 + `정렬` 콤보박스(배정 순서·위 5종). 바꾸면 처음 이미지부터 보고, `다음 미검토`·←/→·A/R은 지금 보는 목록 기준으로 동작한다. 결정한 이미지는 목록에서 바로 사라지지 않고 표시만 바뀌며(보던 목록이 흔들리지 않게), 필터를 바꾸면 반영된다
  - **보기 모드**: `미리보기`(줄인 사본, 기본) / `원본 고정`(원본, 다음 2장은 미리 받음). 선택은 브라우저에 저장
  - 오른쪽 패널: AI 점수·판정, 이상 영역별 사유, 코멘트, 승인/반려, **마지막 검수자·시각**
  - **반려 사유**: 반려(`R`)를 누르면 사유 상자가 열린다. AI가 찾은 원인이 미리 골라져 있고(칩에 `AI` 표시), 숫자키 `1`~`7`로 켜고 끈 뒤 `Enter`로 확정, `Esc`로 취소한다. 사유를 하나도 고르지 않으면 반려되지 않고, `기타`를 고르면 코멘트를 적어야 한다. 이미 반려한 이미지를 다시 반려하면 그때 고른 사유로 시작한다. 반려한 이미지는 검수 결과 아래에 사유가 칩으로 보인다
  - **크게 보기**(`Z`, 이미지 클릭, 오른쪽 위 버튼): 화면 가득 보면서 휠 확대·드래그 이동·더블클릭 맞춤/2배, `원본 크기`(1:1)·`맞춤`, 박스/히트맵 토글, **그 자리에서 승인/반려**
  - **박스 호버 설명**: 박스에는 번호만 보이고, 마우스를 올리면 한글 원인·점수·설명·위치 카드가 뜬다. 오른쪽 이상 영역 목록과 서로 강조된다
- **소요 시간 분석**(관리자): 담당자별 검수 속도, 배정별 소요, 모델 처리 시간, 수신 배치 기록
- **대시보드**(홈): 내 검수 대기, (배정 관리 권한자) 아직 배정하지 않은 의심·불량, AI 판정 분포, 배정 현황, 검수 진행, 최근 7일 검수 건수(막대 차트, `표로 보기`). 이미지 분포는 전체 열람 권한자는 전체·그 외는 내게 배정된 것, 나머지는 관리자는 전체·그 외는 내 것
- **내 배정**: 나에게 배정된 건만(요약 카드도 내 것). 눌러서 점검을 시작한다
- **점검 이력**: 내가 검수(승인/반려)한 기록(반려 사유·코멘트 포함). 결정을 바꾸면 새 기록이 쌓이고 이전 기록은 `번복됨`. 배정 관리 권한자는 `전체`로 모든 담당자의 기록을 본다. 행을 누르면 그 배정이 열린다
- **이미지 목록**: 수신·판정이 끝난 이미지를 AI 판정(건수 칩)·배정 여부·점수/최신 정렬·파일명 검색으로 찾는다. 행을 누르면 보기 전용으로 크게 보고 이전/다음으로 넘겨 본다(쪽의 끝에 닿으면 다음 쪽으로 이어진다). 전체 열람 권한이 없으면 내게 배정된 이미지만 보인다

### 서버
- 인증(JWT httpOnly 쿠키), 역할별 권한(관리자/QA)
- 배정 생성·상태 전이(정해진 다음 단계로만)·점검 내용·이미지 페이지 조회·검수 저장
- **이미지 파일 API** `GET /api/images/:imageKey/thumb|preview|original|heatmap`: 디스크 경로를 노출하지 않고 이미지 ID로 요청. 관리자는 전부, QA는 **자기 배정 이미지만**. 캐시·보안 헤더 적용
- 판정은 `rules` 테이블의 임계값으로만 하고, 판정마다 **모델 버전과 규칙 버전**을 기록

### 파일 수신 워커 (`npm run worker`)
`inbox` 폴더에 이미지를 넣으면 자동으로: 안정 판정(복사가 끝난 파일만) → 매직바이트 검사 → 해시 기록 → 한 장씩 추론 → 판정 저장 → 썸네일·미리보기(webp) 생성 → `done`으로 이동. 실패하면 `failed`로 격리하고 큐는 계속 돈다. 워커는 하나만 실행되고(DB 잠금), 시작할 때 죽다 만 작업을 정리한다.

### 모델 연결부
추론은 **어댑터**로 분리돼 있고 출력은 기획서 5장 JSON 계약으로 고정이다(점수 0~1은 **높을수록 정상**, 박스는 원본 픽셀, 사유 코드에 원인 미분류 `UNKNOWN` 포함). 어댑터는 두 가지다.
- **목 어댑터**(기본): 파일 해시로 만든 가짜 점수·박스. 화면·흐름 시험용이며 점수는 정답과 무관하다.
- **PatchCore 어댑터**(`MODEL_ADAPTER=patchcore`): Python 추론 서버(`python/serve.py`)와 대화하는 실제 모델. 정상 이미지로 학습하고 모델 버전(백본·입력 크기·학습 파일 해시·점수 기준)이 판정마다 기록된다. 설치·학습·평가는 `python/README.md`.

### 데이터 만들기
- `generate-mock.mjs`: SVG 목 이미지 3천 장(부하 테스트용)
- `generate-real.mjs`: **ComfyUI로 실제 PNG** 생성(정상 + 생성 오류 6종, 정답 박스 기록)
- `make-derivatives.mjs`: 이미 수신된 이미지의 썸네일·미리보기 보충

## 4. 처음 실행하기

필요한 것: Node.js 22, Docker Desktop. (이미지 생성은 추가로 ComfyUI.)

```bash
# 1) 환경 파일 (.env는 git에 올리지 않는다)
cp .env.example .env          # 비밀번호·JWT_SECRET(16자 이상) 수정

# 2) DB
docker compose up -d          # 최초 기동 시 db/init/*.sql 자동 적용

# 3) 백엔드
cd backend
npm install
npm run migrate               # 스키마 변경분 적용 (이미 적용된 것은 건너뜀)
npm run load-mock             # 최초 1회: 목 데이터 3천 장 생성 후 DB 적재
npm run dev                   # API 서버, 포트 3000

# 4) 프론트 (다른 터미널)
cd frontend
npm install
npm run dev                   # 화면 http://localhost:5173
```

> **포트 3000이 `EACCES`로 안 열리면** (윈도우가 예약한 범위): backend와 frontend 둘 다 `API_PORT=3101`을 앞에 붙여 실행한다. 예: `API_PORT=3101 npm run dev`.

**데모 계정** (비밀번호는 모두 `1234`): `admin@example.com`(관리자), `qa1@example.com`(김검수), `qa2@example.com`(이점검), `qa3@example.com`(박확인)

**끌 때**: 각 터미널에서 Ctrl+C, DB는 `docker compose down`. (`-v`를 붙이면 **데이터가 지워진다**.)

### 4-2. 워커와 실제 모델
- 파일 수신·추론은 별도 워커가 한다: `cd backend && npm run worker` (하나만 실행). 화면에서 올린 이미지(7-2b 참고)와 수신 폴더에 넣은 이미지가 모두 이 워커를 거친다. 워커를 켜지 않으면 업로드한 이미지는 "수신 대기"로 남는다.
- 기본은 목(mock) 모델이다. 실제 모델(PatchCore)로 돌리려면 `python/` 설치·학습 후 `MODEL_ADAPTER=patchcore npm run worker` — 설치, 학습, 평가 방법은 `python/README.md`. 모델 버전은 판정마다 기록된다.
- 모델 성능은 `python/evaluate.py`로 정답 데이터와 비교해 잰다(첫 결과와 해석은 design.md 9장 마지막).

### 4-3. 개발 DB 상태와 초기화
- DB 구성: `db/init/`(스키마 + 시드: 규칙 v1, 데모 계정, 기본 권한)가 **최초 기동 때만** 적용되고, 이후 변경은 `db/migrations/`(001~012)를 `npm run migrate`가 번호 순서로 한 번씩 적용한다. 기록은 `schema_migrations` 테이블.
- 개발 DB에는 목 이미지 3,000장(`load-mock`)과 실제 생성 이미지 300장(수신 시험)이 들어 있다. 화면 확인용으로 만든 시험 데이터(사용자·임시 권한·업로드)는 확인 후 지우는 것을 원칙으로 한다.
- **완전히 새로 시작**: `docker compose down -v` → `docker compose up -d` → `cd backend && npm run migrate && npm run load-mock`. (`data/images/`의 파일은 별도라 지워지지 않는다. 처음부터면 폴더도 비운다.)
- 사용자 시험 데이터만 지우고 싶을 때는 DB에서 직접 지우지 말고 사용자 관리 화면의 비활성화를 쓴다(이력이 사용자에 연결되어 있다).

### 4-4. 비밀값(.env) 교체
- 대상: `POSTGRES_PASSWORD`(DB 비밀번호), `JWT_SECRET`(로그인 서명 키). 외부에 노출됐을 가능성이 있을 때나 주기적으로 바꾼다. `.env`는 git에 올라간 적이 없다.
- 실행: `cd backend && npm run rotate-secrets` (`--dry-run`은 전제 조건만 확인). `.env`와 **실행 중인 DB 사용자**의 비밀번호를 같이 바꾸고, 새 비밀번호로 접속되는지·옛 비밀번호가 거부되는지 확인한다. 값은 어디에도 출력하지 않고, DB 비밀번호는 명령줄이 아닌 표준입력으로 넘긴다. DB 변경이 실패하면 `.env`를 되돌린다.
- 끝난 뒤: **모든 로그인이 풀리고**(JWT 키 교체), API를 다시 시작해야 새 값을 읽는다(`npm run dev`는 `backend/src/server.mjs`를 저장하면 자동 재시작). 워커·테스트는 다음 실행부터 새 값을 쓴다. DB 컨테이너를 `down -v`로 새로 만들 때도 `.env`의 새 비밀번호가 쓰인다.

## 5. 화면 사용 흐름

### 관리자
1. **신규 배정**: 배정 목록에서 `신규 배정` → 담당자·마감일·판정·장수 → 생성. 이미 배정된 이미지는 다시 담기지 않는다.
2. 담당자가 점검을 끝내면 **확인 완료**. (사전배치 단계는 없다: 이미지는 수신할 때 이미 추론·판정된다)
3. 메뉴 **소요 시간**에서 검수 속도·모델 처리 시간 확인.

### QA 담당자
1. 배정 상세에서 **점검 시작** → `이미지 검수` 탭. 처음 열면 첫 미검토 이미지로 이동한다.
2. 이미지를 보고 **승인/반려**. 승인은 바로 저장되고, 반려는 사유를 골라 확정해야 저장된다(코멘트는 `기타`일 때만 필수). 저장되면 다음 미검토로 넘어간다.
3. 전부 검수하면 **점검 완료** (미검토가 남아 있으면 거부된다).

### 비밀번호 변경 (모든 사용자)
- 상단의 **비밀번호 변경**: 현재 비밀번호를 확인한 뒤 새 비밀번호(8자 이상, 현재와 달라야 함)로 바꾼다. 현재 비밀번호를 틀리면 로그인과 같은 횟수 제한에 센다.
- 관리자가 **임시 비밀번호로 초기화**한 계정은 로그인하면 **비밀번호 변경 화면만** 나온다(다른 메뉴·API는 서버가 막는다). 바꾸면 원래 화면으로 간다. `나중에 하기`는 로그아웃이다.
- 메일이 꺼져 있으면(기본) 관리자 화면에 임시 비밀번호가 한 번 보이고 직접 전달한다. 메일이 켜져 있으면(`MAIL_MODE`) 사용자 메일로만 가고 관리자는 볼 수 없다.

### 단축키 (검수 화면)
| 키 | 동작 |
|---|---|
| `←` `→` | 이전/다음 이미지 |
| `A` | 승인 |
| `R` | 반려 (사유 상자 열기 → `1`~`7` 사유 선택 · `Enter` 확정 · `Esc` 취소) |
| `H` | 오버레이(박스·히트맵) 켜기/끄기 |
| `O` | 원본 고정 ↔ 미리보기 |
| `Z` | 크게 보기 열기 (크게 보기 안에서는 닫기) |

**크게 보기 안에서**: `Esc` 닫기 · `+` `−` 확대·축소 · `0` 맞춤 · `1` 원본 크기(1:1) · `←` `→` 이전/다음 · `A` `R` 승인/반려(반려 사유 상자는 같은 키로 동작, `Esc`는 상자만 닫음) · `H` 박스·히트맵 토글. 이미지 목록의 크게 보기는 보기 전용이라 `A` `R`이 없다.

코멘트 입력칸에 커서가 있을 때는 단축키가 동작하지 않는다.

## 6. 파일 수신 사용법

```bash
cd backend && npm run worker     # API와 별도 프로세스. 하나만 실행 가능
```

1. 이미지를 `data/images/ingest/inbox/` 에 넣는다. (확장자 png/jpg/jpeg/webp/svg, 파일당 50MB 이하, 5초마다 스캔. 복사 중인 파일은 크기·수정시각이 두 번 연속 같을 때만 받는다)
2. 흐름: `inbox` → `processing`(대기·처리 중) → `done`(성공) 또는 `failed`(실패, 사유는 DB `images.error`).
3. 처리가 끝난 이미지는 미배정 상태로 쌓이고, 관리자가 신규 배정으로 담는다.
4. 같은 파일을 다시 넣어도 막지 않는다. 새 이미지로 쌓이고 `origin_image_id`로 처음 수신본과 연결된다.
5. 워커가 죽었다 다시 켜지면 처리 중이던 건을 대기로 되돌려 이어서 처리한다.

### 연계 관리 화면 (관리자, 설정 > 연계 > 연계 관리)
- **목록**: 연계마다 사용 중/꺼짐, 감시 폴더·확장자·주기, 대기/처리 중/완료/실패 건수, 최근 수신 시각. 10초마다 갱신된다.
- **추가**: 이름과 폴더를 정한다. 폴더는 허용 루트(`INGEST_ROOT`, 기본 `data/images/ingest`) 아래 상대 경로이고, 다른 연계가 쓰는 폴더와 겹치면 거부한다(같은 폴더를 두 스캐너가 보면 같은 파일을 두 번 받는다). 새 연계의 폴더는 `source-N/` 아래로 제안한다.
- **수정**: 이름·폴더·확장자·크기 상한·스캔 주기. 워커가 매 주기 DB에서 읽으므로 **워커를 다시 켜지 않아도 반영**된다. 변경 이력(누가·언제·이전 값 → 바뀐 값)이 아래에 쌓인다.
- **끄기/켜기**: 삭제는 없다(이미 받은 이미지가 연계를 가리키므로). 끄면 새 파일을 받지 않을 뿐, 이미 받은 파일의 판정은 계속된다.
- **실패 건 재시도**: 실패 건수가 있으면 "실패 N건 보기 · 재시도"가 나온다. 파일이 실패 폴더에 있는 건만 처리 중 폴더로 되돌리고 새 수신 배치로 묶는다. 이미지가 아니어서, 또는 크기 상한을 넘어서 실패한 건은 설정을 고치지 않으면 다시 실패한다.

## 7-2. 규칙 관리 (관리자, 설정 > 판정 > 임계값/규칙)
화면 구성: 현재 활성 버전과 "재판정 필요" 건수 / 새 버전 만들기(입력하면 **미리보기**로 정상·의심·불량이 몇 장이 되고 몇 장이 바뀌는지) / 재판정(미배정만 또는 배정된 이미지 포함) / 버전 목록(끄기·켜기 = 되돌리기) / 변경 이력. 아래는 화면이 쓰는 API.

판정 임계값(정상 ≥ `normalMin`, 의심 ≥ `suspectMin`, 그 아래 불량)은 `rules` 테이블에 있고 **수정하지 않고 새 버전을 쌓는다**. 활성 규칙 = 켜진 것 중 가장 높은 버전(워커도 같은 기준).

| 요청 | 하는 일 |
|---|---|
| `GET /api/rules` | 버전 목록, 활성 버전, **다시 판정이 필요한 이미지 수**(미배정/배정, 활성 규칙이 아닌 규칙으로 판정된 것) |
| `GET /api/rules/preview?normalMin=0.8&suspectMin=0.4` | 저장하지 않고 "이 값이면 정상/의심/불량이 몇 장이 되고, 몇 장이 바뀌는지" |
| `POST /api/rules` `{normalMin, suspectMin}` | 새 버전 생성(바로 활성). 새로 수신하는 이미지부터 이 규칙으로 판정. **이미 판정된 이미지는 그대로** |
| `POST /api/rules/:id/rejudge` `{scope}` | 저장된 점수에 활성 규칙을 적용해 판정을 추가. `scope`: `unassigned`(기본, 미배정만) / `all`(배정된 이미지까지) |
| `PATCH /api/rules/:id` `{enabled}` | 끄기/켜기. **새 버전을 끄면 이전 버전이 활성이 된다(되돌리기)** — 이후 재판정을 눌러야 판정도 돌아간다. 켜진 규칙이 하나뿐이면 못 끈다 |
| `GET /api/rules/history` | 누가·언제 만들고 켜고 끄고 재판정했는지 |

- 재판정은 모델을 다시 돌리지 않는다. 옛 판정 행은 지우지 않고 그대로 남는다(어떤 규칙 버전으로 판정했는지 기록).
- 기본이 "미배정만"인 이유: 검수자가 보고 있는 AI 판정이 갑자기 바뀌지 않게 하려는 것. 배정된 이미지까지 바꾸려면 `scope: "all"`을 명시한다.

## 7-2b. 이미지 업로드 (설정이 아닌 데이터 > 이미지 > 이미지 업로드, 업로드 권한)
- 파일이나 폴더를 끌어다 놓거나 「파일 선택」「폴더 선택」으로 고른다. 이미지가 아니거나 크기를 넘는 파일은 올리기 전에 제외되고 이유가 보인다. **메모**(선택)를 적고 「N장 업로드 시작」.
- 한 장씩 4장 동시에 전송하며 진행률·남은 시간이 보인다. 일시 중지/이어서/취소가 가능하고, 올리는 중에 창을 닫으려 하면 브라우저가 경고한다. 한 번에 최대 1만 장(`UPLOAD_MAX_BATCH_FILES`). 전송 오류가 난 파일만 「실패 N장 다시 시도」로 다시 올릴 수 있다. 서버가 이미지가 아니라고 거절한 파일은 사유와 함께 남는다.
- 올린 파일은 수신 폴더로 들어가고 **워커가 켜져 있으면** 자동으로 모델 검사를 거친다. 하단 「업로드 이력」에서 올린 사람·장수·처리 현황(완료·수신 대기·검사 중·검사 실패·업로드 실패)을 보고, 「보기」에서 파일별 상태와 사유를 본다. 처리 중인 건이 있으면 5초마다 새로 고쳐진다.
- 이력은 내가 올린 것만 보인다. 「모든 업로드 이력 보기」 권한(기본 관리자)이 있으면 전체/내가 올린 것을 고를 수 있다.

## 7-3. 사용자 관리 (관리자, 설정 > 사용자 > 사용자 관리)
- 상단 필터: 상태(전체/승인 대기/사용 중/만료/비활성, 칸마다 건수), 권한, 이름·이메일·업체·부서 검색. 하단 좌측 콤보박스로 20/50/100/1000건씩 보기.
- **일괄 처리**: 상태 필터를 고른 뒤 체크박스로 고르면 위에 처리 바가 나온다. 승인 대기 = 신청 권한대로 일괄 승인 / 권한 지정 승인 / 일괄 반려, 만료 = 일괄 만료 해제 / 비활성, 사용 중 = 비활성, 비활성 = 재활성. 헤더 체크박스는 현재 페이지만 고르고, 페이지가 더 있으면 "조건에 맞는 전체 N명 선택"이 나온다(100명씩 나눠 처리). 대상이 아닌 사람(이미 처리됨 등)은 건너뛰고 사유를 알려 준다.
- **수정** 버튼: 권한, 사용기한(만료된 사용자에게 미래 날짜를 저장하면 해제), 이름·업체·부서·직급·연락처·업체 주소, 임시 비밀번호 초기화(한 번만 표시), 변경 이력. 승인 대기 사용자는 승인할 권한을 골라 승인·반려한다.
- 만료된 사용자는 로그인 화면에서 **만료 해제 요청**을 보내고, 요청 시각이 만료 목록에 나온다.
- 안전장치: 사용 가능한 관리자가 한 명도 안 남는 처리는 취소되고, 본인 계정은 일괄 비활성·반려에서 빠진다.

## 7-3b. 권한 관리 (관리자, 설정 > 사용자 > 권한 관리)
- 권한(역할) 종류를 만들고 이름·설명을 고친다. **＋ 새 권한**: 코드(영문 소문자·숫자·밑줄, 만든 뒤 변경 불가)·이름·설명(선택)·가입 신청 가능 여부. 새 권한은 메뉴 접근이 없는 상태이므로 만든 뒤 「권한별 메뉴」에서 허용할 메뉴를 정한다.
- 목록의 **수정**에서 이름·설명·가입 신청 가능 여부·표시 순서를 바꾸고 사용 현황과 변경 이력을 본다.
- 권한을 없앨 때는 **「사용 안 함으로 전환」**: 새 가입·승인·권한 변경의 선택지에서만 빠지고 이미 가진 사용자는 그대로 쓴다(다시 사용 가능). **삭제**는 사용자와 변경 이력이 없는 권한만 된다. 관리자 권한은 둘 다 안 된다.
- 설명은 「권한별 메뉴」 표의 권한 이름(점선 밑줄)에 마우스를 올리면 말풍선으로 보인다.

## 7-4. 권한별 메뉴 (관리자, 설정 > 사용자 > 권한별 메뉴)
- 권한(관리자/연구원/QA) × 메뉴·기능 체크 표. 체크를 바꾸고 하단 **저장**을 누르면 그 권한의 사용자에게 메뉴가 보이고/숨겨지며, **서버 API도 같은 표로 막힌다**(로그인 중인 사용자에게도 다음 요청부터 적용). 하단 바에서 변경 요약을 보고 되돌릴 수 있고, 변경 이력은 화면 아래에 남는다.
- 관리자의 「사용자 관리」「권한별 메뉴」는 잠겨 있다(아무도 설정을 못 바꾸게 되는 것 방지).
- 권한이 없는 메뉴는 아예 보이지 않아 클릭할 수 없고, 주소를 직접 열면 "접근할 수 없는 페이지입니다"가 나온다. 서버 API도 같은 표로 막는다.
- 권한이 많으면 상단 "표시할 권한"에서 여러 권한을 골라 그 열만 볼 수 있다(전체 보기로 복귀). 권한 종류는 DB(`roles`)가 정하며, 가입 화면에 노출할 권한은 `roles.signup_selectable`로 정한다.

| 증상 | 원인·해결 |

| API가 `listen EACCES 127.0.0.1:3000` | 윈도우 예약 포트. `API_PORT=3101`로 backend·frontend 모두 실행 |
| `localhost:5173`은 되는데 `127.0.0.1:5173`은 안 열림 | Vite가 IPv6(`localhost`)로 뜬다. `localhost`로 접속 |
| 백엔드 테스트가 전부 실패 | Docker Desktop이 꺼져 있다. 켜고 `docker compose up -d` |
| 이미지가 안 보임/403 | 로그인 필요. QA는 **자기에게 배정된** 이미지만 볼 수 있다 |
| 워커가 "이미 다른 워커가 실행 중" | 워커는 하나만 실행된다. 기존 것을 끄고 다시 실행 |
| 이미지 수신이 안 됨 | 확장자·크기 확인, 복사가 끝났는지(두 번 스캔 필요), 워커가 켜져 있는지, `failed` 폴더와 `images.error` 확인 |
| 한글 제목이 `����`로 깨짐 | 윈도우 셸의 `curl -d`로 한글을 보내면 인코딩이 깨진다. 화면이나 UTF-8 파일(스크립트)로 입력 |
| ComfyUI에 연결 불가 | ComfyUI가 꺼져 있다(`generate-real`이 안내 메시지 후 종료). 8188 포트 확인 |
| 업로드한 이미지가 "수신 대기"에서 안 넘어감 | 워커가 꺼져 있다. `cd backend && npm run worker`. 켜져 있으면 연계 관리의 감시 폴더와 `failed` 폴더 확인 |
| 업로드 화면이 "수신 폴더 연계가 없어…" | 켜져 있는 폴더 연계가 없다. 설정 > 연계 관리에서 만들거나 켠다 |
| `MODEL_ADAPTER=patchcore`인데 워커가 "meta.json을 읽을 수 없습니다" | 아직 학습하지 않았다. `python/README.md`의 학습 단계를 먼저 실행 |
| 비밀값 교체 뒤 화면이 로그인으로 돌아감 | 정상이다(JWT 키가 바뀌어 세션 만료). 다시 로그인. API가 이전 값으로 떠 있으면 `backend/src/server.mjs`를 저장해 재시작 |
| GPU 메모리가 가득 참 | ComfyUI 등 다른 프로그램이 점유 중일 수 있다. 학습·추론은 GPU를 쓰므로 끄고 실행 |

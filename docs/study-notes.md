# 학습 노트 (질문과 답 모음)

대화 중 나온 개념 질문을 나중에 공부할 수 있게 모아 둔 문서. 설계 결정은 [design.md](design.md), 여기는 "무슨 뜻인가"에 집중한다.

---

## 1. 마이그레이션이란?
DB 테이블 구조를 바꾸는 작업(컬럼 추가, 테이블 신설 등)을 **순서가 있는 스크립트 파일**로 남겨 두는 방식. 어느 PC에서나 같은 순서로 적용하면 같은 구조가 된다.
- 지금은 `db/init/*.sql`을 최초 기동 때 한 번만 실행한다. 이미 데이터가 있는 DB의 구조를 바꾸려면 `docker compose down -v`(데이터 삭제)가 필요했다.
- 마이그레이션을 쓰면 데이터를 지우지 않고 `ALTER TABLE`로 바꾼다. 어디까지 적용했는지 `schema_migrations` 같은 표에 기록한다.

## 2. 어댑터란?
"이미지를 주면 정해진 JSON 형식(기획서 5장)으로 답해 주는 상자". 안쪽이 가짜(목)인지 진짜 모델인지는 바깥에서 모른다. 모델을 바꿔도 바깥 코드는 그대로다. 프로젝트 규칙(CLAUDE.md)이기도 하다.
```
infer(이미지 경로) → { 5장 JSON 계약 }
  ├─ MockAdapter  : 파일 해시로 항상 같은 결과를 만들고 지연만 흉내
  └─ HttpAdapter  : (나중에) Python 모델 서비스에 HTTP로 요청
```

## 3. 워커(worker)란?
화면과 무관하게 **뒤에서 일하는 별도 프로그램**. 식당에 비유하면 API는 홀 직원, 워커는 주방이다. 홀이 주문을 받는 동안 주방이 한 접시씩 순서대로 만든다.
- 추론은 오래 걸린다. API 안에서 돌리면 그동안 화면 요청이 느려지거나 막힌다.
- 별도 프로세스로 두면 `npm run worker` 한 줄로 따로 켜고 끌 수 있고, GPU도 이쪽만 쓴다.
- 여러 워커가 같은 일을 가져가지 않도록 DB 큐에서 `FOR UPDATE SKIP LOCKED`로 한 건씩 가져간다.

## 4. scanOnce, processOne
- `scanOnce()`: 감시 폴더를 **한 번 훑어서** 새 파일을 DB에 등록(`PENDING`)하는 함수.
- `processOne()`: 대기 중인 이미지 **1장을 꺼내** 추론하고 결과를 저장하는 함수.
- 워커는 이 둘을 타이머로 반복 호출하는 얇은 껍데기다.
- 함수를 따로 만드는 이유는 **테스트**다. "5초마다 반복" 타이머 안에 로직이 있으면 테스트가 어렵다. 함수 1회 호출로 결과를 바로 확인한다.

## 5. PRECHECKED(사전배치) 제거란?
현재 상태 흐름: `배정 → 사전배치 → 점검중 → 점검완료 → 확인완료`
사전 검증을 파일 수신 시점에 하기로 했으므로, 배정 후의 "사전배치" 단계는 할 일이 없다. 그래서 DB 제약, 서버 상태 전이 표, 화면의 단계 표시와 요약 카드, 테스트에서 이 단계를 지워 4단계로 줄인다. 기능 추가가 아니라 정리 작업이라 순서상 마지막에 둔다.

## 6. 같은 파일인지 알 수 있나? (해시)
파일 이름은 믿을 수 없다 (이름이 같아도 내용이 다를 수 있고, 이름이 달라도 내용이 같을 수 있다). **내용의 해시(sha256)** 는 파일 내용이 한 글자라도 다르면 완전히 다른 값이 나온다. 같은 해시 = 같은 내용.
- 이 프로젝트에서는 해시로 **막지 않는다** (재검증을 허용). 같은 파일이 다시 들어온 것을 **연결해서 보여주는 용도**로 쓴다.

## 7. 중복 정책: 새 행 insert + 자기 참조 외래키
같은 파일이 다시 들어오면 `images`에 **새 행**을 넣고, `origin_image_id`가 처음 들어온 행을 가리킨다.
```
images
 id | image_key | sha256 | origin_image_id
  1 | A         | h1     | NULL      ← 처음 수신
  9 | A-2       | h1     | 1         ← 같은 내용 재수신 (새 행)
```
- 장점: 각 행이 자기 추론 결과와 검수 결과를 따로 가져 기존 검수에 영향이 없다. 쌓기만 하는 기록 원칙과도 맞는다.
- 외래키 = 다른 행을 가리키는 열. 자기 자신의 테이블을 가리키면 "자기 참조"라고 한다.

## 8. 연계 관리 화면은 모니터링인가?
아니다. **연계를 설정하고 추가하는** 화면이다. 모니터링은 "지금 얼마나 처리됐나"를 보는 곳이고, 연계 관리는 "무엇을 어디서 어떻게 받을지"를 정하는 곳이다.
- 연계 목록 → 추가/수정/삭제/켜기·끄기. 연계 하나는 종류(현재 폴더, 이후 DB 등)와 그 종류의 설정을 가진다.
- 목록에는 연계별 요약 상태 정도만 보여주고, 상세 진행 현황은 모니터링 쪽에 둔다.
- 구체적인 화면 구성은 구현 때 목업으로 정한다.

## 9. 테이블 상속(extends)과 공통 컬럼
생각해 둔 공통 컬럼: `id`, 등록자, 등록일시, 수정자, 수정일시.
- PostgreSQL `INHERITS`: 가능하지만 제약조건·인덱스·외래키가 자식에게 따라가지 않아 실무에서는 거의 쓰지 않는다.
- ORM의 base entity 방식: ORM이 있어야 한다. 이 프로젝트는 SQL을 직접 쓰므로 해당 없음.
- 권장: 새 테이블마다 같은 컬럼 이름을 **규칙**으로 적용하고, 수정일시는 **트리거 함수 하나**로 자동 갱신한다. 수정자는 API가 채운다.
- 쌓기만 하는 테이블(`reviews`, `assignment_history`, `model_runs`)은 수정이 없으므로 수정자/수정일시를 두지 않는다.

## 10. 세션을 비우고 이어가기
`CLAUDE.md`는 새 세션이 자동으로 읽고, 거기에 "README → design.md 순서로 읽어라"가 적혀 있다. 그래서 새 세션에서는 **"README.md 읽고 이어서 해줘"** 한 줄이면 된다. 진행 상황은 README, 결정과 이유는 design.md, 개념 설명은 이 문서에 있다.

## 11. 테스트코드는 무엇을 기준으로 만드나?
"이 코드가 **약속한 행동**을 지키는가"가 기준이다. 코드가 어떻게 생겼는지가 아니라 **바깥에서 보이는 결과**를 확인한다. 경계값은 그중 하나일 뿐이다. 이 프로젝트에서 쓰는 관점:
1. **정상 경로**: 파일을 넣으면 수신 → 추론 → DONE이 되고 결과(모델 버전, 규칙 버전, 판정)가 저장되는가.
2. **경계값**: 규칙의 임계값 0.9 / 0.5에서 0.9는 정상, 0.89는 의심, 0.5는 의심, 0.49는 불량인가(`>=`와 `>` 차이를 잡는다). 크기 상한 바로 아래/위, 빈 파일, "처음 본 파일 vs 두 번째 본 파일".
3. **실패 경로**: 모델이 예외를 던지면? 계약을 어기면? 파일이 사라졌으면? → 그 건만 FAILED가 되고 다음 건은 계속 처리되는가. 정상 경로만 테스트하면 장애 때 처음 발견하게 된다.
4. **잘못된 입력/보안**: 확장자만 .png인 가짜 파일, 허용 루트 밖 경로(`../`), 심볼릭 링크.
5. **불변 조건(항상 참이어야 하는 것)**: 같은 건을 두 번 처리하지 않는다, 판정 임계값은 코드가 아니라 rules 테이블을 따른다, 수신 행은 덮어쓰지 않고 쌓는다.
6. **회귀 방지**: 한 번 고친 버그나 정한 정책(재수신은 막지 않고 새 행)은 테스트로 박아 둔다. 나중에 누가 바꾸면 바로 깨진다.

**좋은 테스트인지 확인하는 법 = 변이 검증**: 코드를 일부러 망가뜨려 보고(예: `>=`를 `>`로, 안정 판정 조건 제거) 테스트가 **실패하는지** 본다. 이번에도 두 가지를 깨뜨려 각각 9개, 2개 테스트가 실패하는 것을 확인했다. 깨뜨려도 통과하는 테스트는 아무것도 지켜 주지 못한다.

**단위 vs 통합**: 규칙 판정처럼 입력→출력만 있는 것은 단위 테스트(DB 불필요), 폴더+DB+파일 이동이 얽힌 것은 통합 테스트(임시 폴더와 전용 테스트 DB 사용). 시간이나 반복(타이머)이 섞이면 로직을 함수로 빼고 `now` 같은 값을 인자로 받아 테스트가 직접 제어하게 한다(`runCycle`이 그 예).

**테스트가 말해 주지 못하는 것**: 테스트 통과 = 정해 둔 시나리오가 맞다는 뜻이지 버그가 없다는 뜻이 아니다. 그래서 실제로 워커를 띄워 파일을 넣어 보는 확인도 병행했다.
